# specs/vps -- VPS protocol compatibility layer (Ladder front)

The law lives in `ladder_protocol_map.t27` (9 tests). Every decision the deployed adapter
makes -- model allowlist, request verdicts, supported vs strippable features, effective
max_tokens, stop vocabularies, role mapping (developer -> system), loopback-only bind --
is a function of that spec. The spec is the source of truth; nothing else decides.

Artifacts and deployment (verified 2026-11-11):

- `ladder_protocol_map.generated.mts` -- generated by `t27b ts` from the spec; the committed
  copy is byte-identical to a fresh regeneration (checked in CI-style locally), so drift is a
  failing diff.
- The executable chain on the VPS: agents -> 127.0.0.1:3132 (launchd SSH tunnel,
  com.t27.vps-ladder-tunnel) -> VPS 127.0.0.1:3133 (`ladder-protocol-adapter.service`,
  thin loader) -> 127.0.0.1:3131 (`dsh-ladder.service`) -> zai free rung.
- The thin loader (`protocol-adapter.mjs`, IO glue only: routing, JSON walk, SSE piping; zero
  protocol decisions) is a deployment artifact kept on the VPS at
  `/root/.t27os/bin/protocol-adapter.mjs`, sha256 a3946055b37817a6672b5a50a758d4f1bcca9d0761049a40121a6bbacc57742e .
  It is intentionally NOT committed: it is foreign (non-t27) and under the foreign-line budget;
  its sha256 here pins the reviewed bytes. To change protocol behavior, change the spec,
  regenerate, redeploy -- never edit the loader.

each completed a read->write task through the chain (files verified); law behaviors observed
live: 403 for an off-allowlist model, web_search tool stripped per law, developer role mapped.
Zero paid calls; local LM Studio not used by any agent.
