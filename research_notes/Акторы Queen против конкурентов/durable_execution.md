# Durable execution and stateful serverless vs. a small TS/Bun actor runtime on Postgres (state as of Oct 2026)

Scope: Temporal, Restate (virtual objects), Cloudflare Durable Objects + Agents SDK, Rivet Actors, Dapr actors + Dapr Workflows (+ Dapr Agents), Inngest (+ AgentKit), DBOS, Hatchet, Trigger.dev, plus Postgres queues (graphile-worker, pg-boss). Our reference runtime: TypeScript/Bun BEAM-style actors in one Railway service, mailboxes and actor state in memory, ~30 min drain on deploy, multi-node via Postgres LISTEN/NOTIFY + heartbeats; a 5-step release job (version check, tag check, GitHub release, CI workflow, crates.io) that waited ~90 min on CI.

Convention: "vendor" = number/claim published by the platform's own company; "independent" = third party. Dates given where the source shows one.

## Q1. Execution model: how state, timers and multi-step work survive crashes and restarts

### Takeaway
Every platform in this set persists the progress of a multi-step job outside the process, at step granularity, and resumes it on another process after a crash. The difference is what gets persisted. Temporal, Restate, DBOS, Inngest, Hatchet and Dapr Workflows persist an append-only journal of step results and re-run the function, skipping completed steps. Durable Objects and Rivet persist the actor's own state (SQLite) plus a schedule table, and leave recovery logic to the developer. Trigger.dev snapshots the whole process with CRIU. Timers survive restarts in all of them because a timer is a database row with a wake-up time, never an in-process `setTimeout`. Our runtime keeps mailboxes, state and timers in memory, so a crash loses them and only a graceful drain protects them.

### Cited Findings

**Journal + replay family**
- DBOS (library, not a server): workflow inputs, step outputs, schedule and queue state go into a Postgres "system database". It writes one row per step to checkpoint its outcome, plus one write when a workflow starts and one when it finishes, and calls that "the only overhead DBOS adds". On a single node it scans for PENDING workflows at startup and resumes them. In a distributed setup, Conductor detects a dead executor by its closed websocket and, after a grace period, hands that executor's workflows to a live server. Recovery re-calls the workflow with its checkpointed inputs. Completed steps return their saved outputs, and execution continues at the first step with no checkpoint — [DBOS Architecture docs](https://docs.dbos.dev/architecture)
- DBOS rules: workflow functions must be deterministic, and side effects (DB access, third-party APIs, random numbers, the clock) go in steps. A changed result for the same step throws `DBOSStepNondeterminismError`. `DBOS.sleep()` "saves the wakeup time in the database" and survives restarts. Workflow timeouts (`timeoutMS`) are also durable and cancel the workflow and its children — [DBOS workflow tutorial](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial)
- Restate (Restate 1.2, 2025-02-20): each partition has a replicated log (Bifrost) and an event processor. Events are appended to the log first, and once a replication quorum acks they are applied and the handler receives its ack ("a single network roundtrip for a replication quorum"). Processor state lives in embedded RocksDB, is derived deterministically from the log, and is periodically snapshotted to S3, after which the log is trimmed. Journal entries are step results, invocations, state updates, timers and durable promises. On failure, a new attempt receives the whole journal so far, and events from older attempts are rejected — [Restate blog, "Building a modern Durable Execution Engine from First Principles"](https://restate.dev/blog/building-a-modern-durable-execution-engine-from-first-principles)
- Restate virtual objects: state sits in an embedded K/V store scoped per object key and is journaled together with execution steps. "Only one handler can modify state at a time." On FaaS, Restate "can suspend functions while they wait for external events", so the wait is not paid for — [Restate key concepts](https://docs.restate.dev/foundations/key-concepts). Exclusive handlers queue per key, and shared handlers can read concurrently — [search summary of Restate docs, via Restate vs Temporal page](https://restate.dev/vs/temporal) (not re-verified on the handler docs page)
- Temporal: activity heartbeats tell the service that a worker has not crashed — [Temporal glossary](https://docs.temporal.io/docs/glossary/). "Asynchronous Activity Completion" lets an activity function return without completing the activity. An outside system later completes it, or heartbeats it, through the client using a task token or (namespace, workflowId, activityId). Temporal recommends this over signals when "the external system is unreliable and might fail to Signal, or you want the external process to Heartbeat or receive Cancellation" — [Temporal TS async activity docs](https://docs.temporal.io/develop/typescript/activities/asynchronous-activity.md); [Python version](https://docs.temporal.io/develop/python/activities/asynchronous-activity.md)
- Inngest: each `step.run()` result is saved as a checkpoint. "When a run resumes, Inngest re-enters your function and returns each completed step's saved result." `step.waitForEvent()` (example timeout 24h) leaves the run suspended, so it "holds no worker and no connection". `step.sleep()` / `step.sleepUntil()` cover timed pauses. Run state is capped at 32 MiB and a step result at 4 MiB — [Inngest Durable Agents docs](https://www.inngest.com/docs/learn/durable-agents)
- Hatchet durable tasks: SleepFor, WaitForEvent, WaitFor, Memo and RunChild each write a checkpoint to a "durable event log". During a wait the task is evicted from its worker, which frees the slot, and it can resume on a different worker. On resume Hatchet replays the event log and re-runs the code path, skipping completed operations. A sleep keeps its original deadline: "if interrupted after 23 of 24 hours, only sleeps 1 more hour". An event that arrives while the task is evicted is still delivered from the log — [Hatchet durable tasks docs (llms.txt mirror)](https://docs.hatchet.run/llms/v1/durable-tasks.md); [Hatchet task eviction](https://docs.hatchet.run/llms/v1/task-eviction.md)
- Dapr Workflows: the engine is embedded in the Dapr sidecar and built on `durabletask-go`. Workflow state is stored through actors in a state store as an append-only history. One-shot reminders drive execution, and after a node or sidecar crash the reminder reactivates the actor and retries "forever". Records written per operation: workflow start 5, activity call 3, timer 3, raised event 3, child workflow start 8 — [Dapr workflow architecture](https://docs.dapr.io/developing-applications/building-blocks/workflow/workflow-architecture/)

**Keyed single-threaded object family**
- Durable Objects: each object is single-threaded. An input gate blocks new events while synchronous JS runs, and an `await` on fetch reopens it. SQLite calls are synchronous and atomic. Output gates hold a response "until all storage writes relevant to the response have been confirmed", and if the write fails the response becomes an error and the object restarts. Gates do not serialize a whole handler across external awaits — [Cloudflare docs, "Rules of Durable Objects"](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/) (via search summary); [Cloudflare blog, "Durable Objects: Easy, Fast, Correct"](https://blog.cloudflare.com/durable-objects-easy-fast-correct-choose-three/)
- DO alarms: one alarm per object, and `setAlarm()` overwrites it. "Guaranteed at-least-once execution", retried with exponential backoff from 2 s for up to 6 retries, after which nothing runs until `setAlarm` is called again. If the object dies unexpectedly, `alarm()` may be re-run "on another machine". To handle many events, keep them in storage and have the alarm reschedule itself for the next one — [DO Alarms API](https://developers.cloudflare.com/durable-objects/api/alarms/)
- Cloudflare Agents SDK on DOs: `this.state`, SQL tables, schedules and fiber checkpoints survive hibernation and restarts. "In-memory variables, timers, open fetches, and local closures do not survive eviction." Eviction comes from deploys, platform restarts or resource limits and "can happen at any point". Idle eviction happens after about 70-140 s. `keepAlive()` / `keepAliveWhile()` hold the object awake. `schedule()` / `scheduleEvery()` store entries in SQLite and arm the single alarm. `runFiber()` registers a row before work starts, `stash()` checkpoints, and `onFiberRecovered()` runs after eviction. Recovery is not automatic replay: "you decide what recovery means for your domain" — [Cloudflare Agents, Long-running agents](https://developers.cloudflare.com/agents/concepts/agentic-patterns/long-running-agents/)
- The Agent class keeps its schedules in a SQL table (`cf_agents_schedules`) and points the one DO alarm at whichever is due next — [third-party analysis, Truvisory](https://truvisory.com/agents-mcp/agents-sdk-durable-objects/) (secondary)
- Rivet Actors: "a long-lived process with durable state, a queue, realtime connections, and scheduling". Actors sleep when idle and wake on the next request with state intact. Workflows add "recorded steps, retries, and replay for work that outlives a process", and every workflow is an actor — [Rivet actors docs](https://rivet.dev/docs/actors/). `schedule.after` / `schedule.at` / `cron.set` / `cron.every` (minimum 5 s) schedules "survive actor sleep, restarts, upgrades, and crashes". Failed one-shot schedules are not retried, and overlapping recurring runs are skipped — [Rivet schedule docs](https://rivet.dev/docs/actors/schedule). State is automatically persisted to embedded SQLite, FoundationDB or Postgres "with no explicit save calls" — [openapps directory](https://openapps.pro/apps/rivet) (secondary). The Rivet landing page lists "Postgres or FoundationDB for persistence and tiered storage to S3" — [rivet.dev](https://rivet.dev/)
- Dapr actors: turn-based, so "no other actor methods or timer/reminder callbacks will be in progress until this callback completes". State changes are saved when the callback finishes, and if the save fails the actor is deactivated and a new instance activated. Timers are in-memory and lost on deactivation ("Dapr actor runtime is not retaining any information about timers after deactivation"). Reminders persist "across actor deactivations and failovers" and are stored in the Dapr Scheduler. Reminder failure policy is `drop` or `constant`, defaulting to 3 retries at 1 s — [Dapr actor timers and reminders](https://docs.dapr.io/developing-applications/building-blocks/actors/actors-timers-reminders/). In Dapr 1.15 (Feb 2025) the Scheduler became production-ready and the default backend for actor and workflow reminders. Upgrading from 1.14 to 1.15 wipes the Scheduler data directory — [Diagrid, Dapr 1.15 highlights](https://www.diagrid.io/blog/dapr-1-15-release-highlights); [Dapr v1.15 release post](https://blog.dapr.io/posts/2025/02/27/dapr-v1.15-is-now-available/)

**Process snapshot family**
- Trigger.dev: on a child-task wait or a timed wait, CRIU checkpoints the process (memory, registers, file descriptors), the compute is released, and the snapshot is later restored in a new environment — [indepth.dev, how Trigger.dev checkpoints containers](https://indepth.dev/posts/1020/en/how-trigger-dev-checkpoints-containers); [Trigger.dev "How it works"](https://trigger.dev/docs/how-it-works). The docs say `wait.for()` under 60 s does not checkpoint, but the pricing FAQ says waits over 5 s are checkpointed; this conflict is unresolved — [search summary of Trigger.dev docs and pricing](https://trigger.dev/pricing). Waitpoints (v4) can block many runs, and one run can be blocked by many waitpoints. A run waiting for a human is checkpointed and resumes via SDK, React hook or webhook callback URL — [Trigger.dev v4 GA](https://trigger.dev/launchweek/2/trigger-v4-ga). In the 2024-era alpha, a checkpoint was "synchronous and takes ~500ms" — [Run Engine 2.0 alpha](https://trigger.dev/launchweek/0/run-engine-2-alpha) (old). As of the v4 GA page, checkpoints are not available when self-hosting — [Trigger.dev v4 GA](https://trigger.dev/launchweek/2/trigger-v4-ga) (may have changed)

### Inferences
- The model that matches our runtime most closely is Restate virtual objects / DO / Rivet / Dapr actors: a single writer per key with a mailbox. What those systems add is that the mailbox (inbox) and state commit to storage on every turn, and timers are stored rows. Dapr's "save state at end of each turn" is the cheapest version of this.
- Our ~90 min wait on CI is exactly the case each platform handles by suspending: Temporal async completion, Restate awakeable, Inngest `waitForEvent`, Hatchet WaitForEvent with eviction, DBOS recv/sleep, Trigger.dev waitpoint, and CF "save a job ID, hibernate, wake on callback". The last one is the Project Think pattern, which names CI explicitly (see Q6). None of them holds a process for 90 minutes, so none needs a 30-minute drain to protect a waiting job.
- The DO/Agents SDK lesson that "timers and open fetches do not survive eviction" describes our current in-memory timers. Our drain is the equivalent of `keepAlive()`, which only works for planned evictions.

### Gaps
- No primary source found for Restate's exclusive vs shared handler semantics beyond the summary. The handlers page was not fetched.
- Rivet's state persistence semantics (when exactly the state is flushed, and on which backend) come from the docs overview and a secondary directory only. The lifecycle page was not fetched.
- DO SQLite durability internals (replication of the WAL to followers, point-in-time recovery) are in Cloudflare's 2024 "Zero-latency SQLite storage in every Durable Object" post ([blog](https://blog.cloudflare.com/sqlite-in-durable-objects/)), which was not fetched in this session, so no numbers are quoted.

## Q2. Delivery semantics: exactly-once vs at-least-once + idempotency keys; how they deduplicate

### Takeaway
No platform here claims exactly-once side effects for arbitrary external calls. They split the problem in two. (a) Starting a workflow is deduplicated: a workflow/run ID or idempotency key is a unique key, so a second start returns the existing run. (b) Steps are at-least-once until their result is recorded, and exactly-once after. The window between "external call succeeded" and "result recorded" is the developer's job: idempotency keys or natural checks. Exactly-once is real only when the step's side effect lives in the same database transaction as the checkpoint (DBOS transactions) or inside the engine's own log (Restate state/journal entries under leader fencing).

### Cited Findings
- DBOS: an assigned workflow ID "acts as an idempotency key". By default, starting with an existing ID "returns a handle to the existing workflow". `workflowIDReusePolicy: 'reject'` throws instead. "Steps are tried at least once, but a completed step is never re-executed. Transactions commit exactly once." A workflow that throws an uncaught exception goes to `ERROR` and is not recovered — [DBOS workflow tutorial](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial). A step in progress at crash time is retried, so steps should be idempotent — [DBOS Architecture](https://docs.dbos.dev/architecture)
- Restate: invocations "run exactly once regardless of failures". With an idempotency key, "Duplicate requests will return the same result as the original request" — [Restate key concepts](https://docs.restate.dev/foundations/key-concepts). Mechanically, the partition processor checks the idempotency key in partition state and atomically adds the key and starts the invocation. Leader epochs fence old leaders, so "any step / activity result is committed exactly once". Invocations are routed to partitions by hash of the object key, workflow ID or idempotency key — [Restate first-principles blog](https://restate.dev/blog/building-a-modern-durable-execution-engine-from-first-principles)
- Inngest: event-level dedupe by event ID within 24 h. Function-level `idempotency` is a CEL expression over event data. Inngest's guidance: a step "does not make an external action exactly once", so use idempotency keys for writes, payments and messages, and "don't use a new retry attempt ID as the external idempotency key" — [Inngest idempotency docs](https://www.inngest.com/docs/durable-execution/guides-and-advanced/idempotency); [Inngest handling idempotency guide](https://www.inngest.com/docs/guides/handling-idempotency); [Inngest blog on fault-tolerant event-driven systems](https://www.inngest.com/blog/build-more-reliable-workflows-with-events)
- Hatchet: the core engine is at-least-once ("a task can run more than once"), with state transitions persisted transactionally in Postgres — [Hatchet architecture & guarantees](https://docs.hatchet.run/v1/architecture-and-guarantees). The durable-task docs claim that replaying from checkpoints on retry "gives your tasks exactly-once semantics" — [Hatchet durable tasks](https://docs.hatchet.run/llms/v1/durable-tasks.md). That is a vendor claim scoped to completed checkpoints, and the two pages differ in emphasis.
- Temporal: activity IDs are unique only among open activities of one workflow run. Standalone activities have their own ID space with `USE_EXISTING` / `REJECT_DUPLICATES` style policies — [Temporal activity execution docs](https://docs.temporal.io/activity-execution.md). Activities retry by default, so they are at-least-once (search summary; not verified on a Temporal page this session)
- Cloudflare DO alarms: "guaranteed at-least-once execution". `deleteAlarm()` inside `alarm()` is only a best-effort stop to retries — [DO Alarms API](https://developers.cloudflare.com/durable-objects/api/alarms/). Agents SDK `startFiber()` adds an idempotency key and retained status records — [Cloudflare long-running agents](https://developers.cloudflare.com/agents/concepts/agentic-patterns/long-running-agents/)
- Dapr: actor reminders follow a retry policy and "There may be additional retries" from the resiliency policy, with no explicit exactly-once statement — [Dapr timers & reminders](https://docs.dapr.io/developing-applications/building-blocks/actors/actors-timers-reminders/). Workflow activities are retried after a crash via reminders, which implies at-least-once — [Dapr workflow architecture](https://docs.dapr.io/developing-applications/building-blocks/workflow/workflow-architecture/). A community report (Azure managed Dapr 1.16.4) says reusing deterministic instance IDs left retention reminders that saturated the Scheduler and stuck workflows in PENDING; the poster marks the root cause as suspected — [Microsoft Q&A thread](https://learn.microsoft.com/en-za/answers/questions/5947887/managed-dapr-1-16-4-scheduler-not-firing-workflow) (unconfirmed)
- Rivet schedules: no formal guarantee is stated. Failed one-shots are not retried, and actions "should be idempotent so manual retries are safe" — [Rivet schedule docs](https://rivet.dev/docs/actors/schedule)
- Trigger.dev: retries are locked to the run's original version — [Trigger.dev atomic deployments / versioning](https://trigger.dev/docs/deployment/atomic-deployment)

### Inferences
- For the release job this means: step 1 (version check) and step 2 (tag check) are read-only and naturally idempotent. Step 3 (create GitHub release) and step 5 (crates.io publish) are the non-idempotent ones. Both are detectable after the fact: the release exists for the tag, or crates.io already has that version. The standard pattern is "check, then act, then record", with the check repeated on replay. Step 4 (CI) should be keyed by the commit SHA / workflow run ID, not re-dispatched.
- A unique constraint on `(workflow_id)` plus `INSERT ... ON CONFLICT DO NOTHING RETURNING` reproduces the DBOS/Restate start-dedupe in one statement.
- Restate's leader epoch fencing maps to a cheap Postgres equivalent: store an `owner_epoch` / lease generation on each run row and make every step-checkpoint write conditional on it. A zombie node that lost its heartbeat lease then cannot overwrite the new owner's progress. This matters because our multi-node mode uses heartbeats, and a heartbeat timeout alone does not stop a slow old owner from writing.

### Gaps
- No primary Temporal page on activity at-least-once semantics or Workflow ID reuse/conflict policies was fetched this session.
- Inngest's function-level idempotency key retention window was not confirmed.

## Q3. Deploys and versioning: in-flight work across code changes; zero-downtime deploys

### Takeaway
There are three strategies, and most platforms offer more than one. (1) **Pin**: each run is bound to the code version it started on, and old workers or endpoints stay alive until their runs drain. Used by Temporal Worker Versioning "Pinned", Restate immutable deployments, Trigger.dev version locking, and DBOS application versions. (2) **Patch**: a run moves to new code, and code branches on a recorded marker (Temporal `patched`, DBOS `DBOS.patch`). (3) **Match by step ID**: Inngest re-runs new code but returns memoized results for step IDs it already has, so adding steps is safe without markers. Snapshot and actor systems (Durable Objects) simply restart the object on new code and rely on state in storage. Because durable runs that are waiting hold no process, a deploy only has to wait for currently executing steps, not for long waits. Our 30-minute drain is a stand-in for that, and it cannot cover a 90-minute CI wait.

### Cited Findings
- Temporal Worker Versioning: Pinned workflows "run on the same worker and build until they complete" and need no patches. Auto-Upgrade workflows move to each new target version and "need to be kept replay-safe manually, that is with patching". Temporal recommends Worker Versioning over patching when versioned deployments are possible, and Auto-Upgrade (not pinning) for blue-green; pinning fits "rainbow" deployments. `DrainageStatus` reports when an old version is Draining or Drained — [Temporal Worker Versioning docs](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning). GA for Worker Versioning was announced together with a public preview of Upgrade-on-Continue-as-New — [Temporal blog](https://temporal.io/blog/ga-worker-versioning-public-preview-upgrade-on-continue-as-new). The changelog places the GA after a Feb 24, 2026 entry, so the GA date is inferred to be 2026 — [Temporal server changelog](https://temporal.io/changelog/product-area/server). Server v1.32 added one-time versioning overrides and lets child workflows choose Pinned/Auto-Upgrade independently of the parent — [Temporal releases](https://github.com/temporalio/temporal/releases). The Kubernetes Temporal Worker Controller automates versioned rollouts — [temporal-worker-controller](https://github.com/temporalio/temporal-worker-controller). Sources conflict on whether the controller and Upgrade-on-CaN are GA.
- Restate: each deployment gets "an immutable, unique endpoint". "Existing requests continue on the original deployment" and "Restate automatically routes new requests to the latest deployment." Draining is done by checking `restate deployment describe <id> --extra`, and the K8s operator scales drained versions to zero. Restate's advice: "Avoid long-running handlers (days or months)". Break them up with delayed calls. "Virtual Object state persists across versions. Ensure your state schema remains backward compatible." Removing or renaming handlers is a breaking change that requires `--breaking` — [Restate versioning docs](https://docs.restate.dev/operate/versioning); see also [Restate blog, "Solving durable execution's immutability problem"](https://restate.dev/blog/solving-durable-executions-immutability-problem) (not fetched)
- DBOS: the application version defaults to a hash of the workflow source code, and recovery "only recovers workflows whose version matches the current application version". Patching: `enablePatching: true`, `DBOS.patch('name')` returns true for new runs and false for old ones, then `DBOS.deprecatePatch` for a transition period, then delete. A patch writes a marker row to `operation_outputs`. Blue-green: start new processes, keep old ones draining, enqueue to `getLatestApplicationVersion()`, and retire the old version when `listWorkflows` with statuses ENQUEUED/DELAYED/PENDING for it is empty. Roll back with `setLatestApplicationVersion()` — [DBOS upgrading workflows](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows). Conductor computes the executors each version needs, so autoscalers can drain old versions to zero — [DBOS Architecture](https://docs.dbos.dev/architecture)
- Inngest: no version numbers. Saved step results are keyed by step ID, with a counter for loops. Adding a step runs it when reached. Editing a completed step's body does not affect runs past it. Renaming an ID makes it a new step, which re-runs side effects. Removed steps' results are ignored — [Inngest versioning guide](https://www.inngest.com/docs/durable-execution/guides-and-advanced/versioning); [Inngest function versioning](https://www.inngest.com/docs/learn/versioning)
- Trigger.dev: each deploy creates an immutable version, and a run "is locked to the current version" when it starts, together with its retries. Trigger-and-wait children inherit the parent's version. Delayed runs lock when they begin executing. Dashboard replays use the current version — [Trigger.dev atomic deployment](https://trigger.dev/docs/deployment/atomic-deployment); [Trigger.dev deployment overview](https://trigger.dev/docs/deployment/overview). Version-skew protection (CLI/SDK v4.5.12+) pins runs to an external deployment ID such as a commit SHA. A run for an unknown ID waits up to 1 h and then expires — [Trigger.dev CLI deploy](https://trigger.dev/docs/cli-deploy-commands)
- Cloudflare DO: moving an object to a new version restarts it and disconnects its WebSockets. Gradual deployments assign versions per object. The constructor must rebuild memory from storage — [third-party book, Architecting on Cloudflare ch. 6](https://architectingoncloudflare.com/chapter-06/). A user report: rapid back-to-back deploys left an object in a reset loop ("Durable Object reset because its code was updated"), and the workaround was waiting 5-10 min between deploys — [GitHub issue, cloudflare/moltworker #238](https://github.com/cloudflare/moltworker/issues/238) (user report). Agents SDK: redeploy evicts the agent, fiber checkpoints survive, open fetches are abandoned — [Cloudflare long-running agents](https://developers.cloudflare.com/agents/concepts/agentic-patterns/long-running-agents/)
- Dapr Workflows: all replicas must register "the exact same set of workflows and activities". The architecture page gives no in-flight versioning story — [Dapr workflow architecture](https://docs.dapr.io/developing-applications/building-blocks/workflow/workflow-architecture/)
- Rivet: schedules survive "upgrades". Recurring jobs whose action no longer exists are deleted — [Rivet schedule docs](https://rivet.dev/docs/actors/schedule)

### Inferences
- The cheapest robust option for us is the DBOS model: store `app_version` (a hash of the job-definition source, or the git SHA) on every run row. A node only resumes or steps runs whose version it can execute. Old-version nodes drain only runs that are actively executing a step, because suspended runs (waiting on CI) need no process. When the wait resolves they are picked up by any compatible node, and pinned runs stuck on a vanished version can be explicitly migrated or patched.
- For a 5-step job, Inngest-style "match by stable step name" is simpler than Temporal-style replay. Name the steps (`version_check`, `tag_check`, `gh_release`, `ci`, `crates_publish`), store their results by name, and on resume skip any named step that has a result. That works across most code changes without version markers. The Inngest caveat applies: renaming a step re-runs it.
- Restate's "avoid handlers that run for days; split with delayed calls" lines up with our problem. A job waiting 90 min should not be one live handler. It should be "dispatch CI, record run ID, park until webhook/poll timer".

### Gaps
- Exact GA dates for Temporal Worker Versioning, Upgrade-on-Continue-as-New and the Worker Controller conflict between sources.
- Official Cloudflare documentation on what happens to an in-flight DO request at the moment of a code update was not found. The only evidence is a third-party book and a user bug report.
- Whether a Trigger.dev checkpointed run restored after a new deploy keeps its locked version is not stated, though version locking implies it does.

## Q4. Postgres-backed approaches (DBOS, Hatchet, graphile-worker, pg-boss; Restate's storage) - scale and per-step overhead

### Takeaway
Postgres-only durable execution is proven up to tens of thousands of steps per second on one database server, according to vendor benchmarks. One Postgres commit per step costs about 1-2 ms in DBOS's figures. Restate does not use Postgres: it uses its own replicated log, RocksDB and S3. Hatchet charges at least about 5 transactions per task and documents only "hundreds of tasks/sec per engine instance" as typical. LISTEN/NOTIFY has a known global-lock scaling problem, and DBOS (2026) recommends batching NOTIFYs and treating them as hints with a polling fallback. At our scale (a handful of jobs, tens of steps per hour) Postgres capacity is not a factor. Correctness of the step journal and lease fencing is.

### Cited Findings
- DBOS (vendor): "a single Postgres database can sustain a throughput of >40K workflows or steps per second". Shard across databases beyond that, and keep step outputs small (store blobs elsewhere and return pointers) — [DBOS Architecture](https://docs.dbos.dev/architecture). Their scaling benchmark reports 144K raw writes/s and 43K no-op workflows/s on one Postgres server, limited by WAL flush to disk — [DBOS blog, Benchmarking workflow execution scalability on Postgres](https://www.dbos.dev/blog/benchmarking-workflow-execution-scalability-on-postgres). Per-step checkpoint is "a single database write per step, which takes less than a millisecond" — [DBOS vs AWS Step Functions benchmark](https://www.dbos.dev/blog/dbos-vs-aws-step-functions-benchmark) (about 21 months old, ~early 2025), elsewhere "a single Postgres write (1-2ms)" — [DBOS vs Temporal](https://www.dbos.dev/compare/dbos-vs-temporal)
- Independent check of DBOS (CockroachDB, a competitor of Postgres): rerunning the raw-write test on RDS PostgreSQL 17 peaked at 62,990 writes/s, versus DBOS's 144K. Local WAL flush was ~1.9 ms p50, versus ~4-8 ms p50 for a cross-AZ Raft quorum on CockroachDB. Sequential commits make end-to-end workflow time roughly 4x one write's latency — [Cockroach Labs blog, Embedded durable execution with DBOS](https://www.cockroachlabs.com/blog/embedded-durable-execution-dbos-cockroachdb/)
- DBOS queues: one secondary report says DBOS's Postgres queue reached 30,600 workflows/s, and that DBOS's queue earlier could not exceed ~100 workflows/s without a locking pattern. After adopting `SKIP LOCKED`, a second ceiling near ~1,000/s appeared from serialization errors in dequeue transactions, and later work raised it — [runtimewire summary](https://runtimewire.com/ja/article/dbos-postgres-queues-30600-workflows-per-second) (secondary; primary DBOS post not fetched). App servers poll queues periodically, and flow control covers per-queue worker concurrency and rate limits — [DBOS Architecture](https://docs.dbos.dev/architecture)
- DBOS on LISTEN/NOTIFY (July 24, 2026): committing a transaction that issued NOTIFY takes a global exclusive lock from commit start until the flush to disk. That serializes commits and defeats group commit. A trigger that NOTIFYs per write topped out at 2.9K writes/s. Buffering NOTIFYs in memory and flushing them in one periodic batch transaction reached up to 60K stream writes/s with 15-100 ms latency, CPU-bound. Recommendations: notifications are hints, the table is the source of truth, and readers keep a low-frequency polling fallback for notifications lost in a crash. A Postgres 19 patch does not remove the global lock — [DBOS blog, Postgres LISTEN/NOTIFY actually scales](https://www.dbos.dev/blog/postgres-listen-notify-scalability); code at github.com/dbos-inc/dbos-postgres-benchmark
- Hatchet (vendor docs): "PostgreSQL is the source of truth", RabbitMQ is optional. Postgres-only deployments "often handle hundreds of tasks/sec per engine instance", reaching "high tens of thousands" with tuning and sharding. Dispatch latency is "often sub-50ms", about 25 ms P95 with hot workers. Listed as a poor fit: sustained 10,000+ tasks/s without sharding, sub-ms dispatch, and serverless-only workers — [Hatchet architecture & guarantees](https://docs.hatchet.run/v1/architecture-and-guarantees). The README says it was load-tested to 10k tasks/s but "consumes more resources than a system built on Redis or RabbitMQ" — [hatchet-dev/hatchet](https://github.com/hatchet-dev/hatchet). The v1 Show HN says "every task in Hatchet corresponds to at minimum 5 Postgres transactions", with bursts above 5k tasks/s on Hatchet Cloud and >20k tasks/min (>1B/month) — [Show HN: Hatchet v1](https://news.ycombinator.com/item?id=43572733) (2025). Batched inserts reached ~37k rows/s — [Hatchet blog, fastest Postgres inserts](https://hatchet.run/blog/fastest-postgres-inserts). Hatchet's multi-tenant fair queueing in Postgres — [Hatchet blog, multi-tenant queues](https://hatchet.run/blog/multi-tenant-queues)
- graphile-worker (vendor docs): average latency from trigger in one process to execution in another is under 3 ms. A 12-core DB server "can queue around 99,600 jobs per second and can process around 11,800 jobs per second". Throughput is capped by the DB, and past that point adding workers lowers performance. Keep the jobs table small — [graphile-worker performance](https://worker.graphile.org/docs/performance); [graphile-worker scaling](https://worker.graphile.org/docs/scaling)
- pg-boss: no published throughput benchmark found.
- Restate storage is not Postgres: Bifrost replicated log, RocksDB per partition, snapshots to S3 — [Restate first-principles blog](https://restate.dev/blog/building-a-modern-durable-execution-engine-from-first-principles)
- Rivet supports Postgres as a persistence backend. Release v2025.37 lists "3x faster networking with Postgres driver" — [Rivet changelog/blog index](https://rivet.dev/blog/). RivetKit's July 2025 launch shipped Redis, filesystem, Rivet Cloud and Cloudflare drivers, and said Postgres "and more are trivial to add" — [RivetKit launch post](https://rivet.dev/changelog/2025-07-01-introducing-rivetkit-backend-libraries-that-replace-saas/)
- Dapr workflows on an RDS-backed actor state store (vendor benchmark, 3-node EKS t2.medium, 15 no-op sequential activities per workflow): 1,000 workflows / 1 replica took ~1m31s on 1.16 vs ~1m40s on 1.15. 10,000 workflows crashed on 1.15 and took ~15m7s on 1.16 — [Dapr v1.16 release post](https://blog.dapr.io/posts/2025/09/16/dapr-v1.16-is-now-available/) (Sept 2025). This works out to roughly 165 activities/s on that small cluster (inferred: 10,000 x 15 / 907 s).

### Inferences
- Our release job writes 5 step checkpoints per release, and a fleet of actors may produce thousands of mailbox messages per hour. DBOS-style checkpointing on our existing Railway Postgres adds roughly 1-2 ms per step plus one write per message if mailboxes are persisted. That cost is negligible next to steps that take seconds to 90 minutes.
- Our use of LISTEN/NOTIFY with heartbeats for multi-node falls inside the regime DBOS warns about only at high write rates. Still, the design lesson applies at any rate: NOTIFY must be a wake-up hint, never the delivery itself. A node that misses a NOTIFY during a restart must find the work by polling the table.
- graphile-worker's "keep the jobs table small" and Dapr's "purge or retention policy" point to one more operational requirement: completed journals need retention and deletion, or the hot table bloats.

### Gaps
- No independent end-to-end per-step p95/p99 measurement on Postgres for DBOS, Hatchet or graphile-worker was found.
- No pg-boss throughput figures were found.
- The primary DBOS queue-performance post (30.6K workflows/s, SKIP LOCKED ceilings) was not fetched, and the numbers come from a secondary summary.

## Q6. AI-agent positioning in 2025-2026 and agent-specific features

### Takeaway
By 2026 every vendor in this set markets itself as the durable runtime for AI agents. The common feature set is: (1) each LLM call and each tool call is a journaled step, so a crash does not re-bill completed model calls; (2) human-in-the-loop as a durable promise or event wait that suspends at zero compute for hours to months; (3) resumable streaming of model output after a crash or redeploy; (4) one actor or durable object per agent or session, with its own state or SQLite. Cloudflare (Agents SDK, Project Think, Apr 2026) and Rivet ("the primitive for agent orchestration") come from the actor side. Temporal (OpenAI Agents SDK integration, GA Mar 2026), Restate (Vercel AI SDK middleware, OpenAI Agents `DurableRunner`), Inngest (AgentKit + durable agents), Dapr (Dapr Agents 1.0, Mar 2026) and Trigger.dev (waitpoints) come from the workflow side.

## Q7. Which ideas a small TypeScript actor runtime on Postgres could adopt cheaply

### Takeaway
The highest-value, lowest-cost borrowing is the DBOS pattern inside our existing Postgres. Persist every multi-step job as a run row plus one checkpoint row per named step. Make waits (CI, human approval, sleeps) into rows with a deadline, not live promises. Version each run with a code hash. Treat LISTEN/NOTIFY as a hint over a polled table. Fence stale owners with a lease epoch. This removes the need for the 30-minute drain for anything that is waiting, and makes the 90-minute CI wait survive deploys and crashes. Only the step running at that instant is ever at risk, and it is re-run idempotently.

### Cited Findings (the specific mechanisms being borrowed)
- One write per step, one at start and one at end. Resume = re-call with saved inputs and return saved outputs for completed steps — [DBOS Architecture](https://docs.dbos.dev/architecture)
- Workflow ID = idempotency key, and a duplicate start returns the existing handle. Durable sleep stores the wake-up time in the DB. Durable timeouts — [DBOS workflow tutorial](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial)
- Version = hash of workflow source. Recover only matching-version runs. `patch()` markers in the step table. Drain old versions only while ENQUEUED/DELAYED/PENDING runs exist for them — [DBOS upgrading workflows](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows)
- Steps keyed by stable name, with a counter for loops. New steps run, finished steps are skipped, renamed steps re-run — [Inngest versioning](https://www.inngest.com/docs/durable-execution/guides-and-advanced/versioning)
- One alarm per object plus a SQL schedule table, and the alarm reschedules to the next due row — [DO Alarms API](https://developers.cloudflare.com/durable-objects/api/alarms/); [Cloudflare long-running agents](https://developers.cloudflare.com/agents/concepts/agentic-patterns/long-running-agents/)
- Wait for event by key with an optional filter. Events arriving while the waiter is evicted are kept in the log. Sleep remembers its original deadline across restarts. Evict waiting tasks from worker slots — [Hatchet durable tasks](https://docs.hatchet.run/llms/v1/durable-tasks.md); [Hatchet task eviction](https://docs.hatchet.run/llms/v1/task-eviction.md)
- For long external jobs (CI): store the external job ID, hibernate, wake on callback — [Cloudflare Project Think](https://blog.cloudflare.com/project-think/). Or async activity completion, where the external party completes the step by token and can heartbeat it — [Temporal async activity](https://docs.temporal.io/develop/typescript/activities/asynchronous-activity.md)
- Leader/attempt fencing: reject events from older attempts and fence old leaders by epoch — [Restate first-principles blog](https://restate.dev/blog/building-a-modern-durable-execution-engine-from-first-principles)
- Batch NOTIFYs, treat them as hints, and keep a polling fallback — [DBOS LISTEN/NOTIFY post](https://www.dbos.dev/blog/postgres-listen-notify-scalability)
- `SKIP LOCKED` dequeue, keep the jobs table small, and expect the DB to be the throughput ceiling — [graphile-worker performance](https://worker.graphile.org/docs/performance); [graphile-worker scaling](https://worker.graphile.org/docs/scaling)
- Save actor state at the end of each turn, and deactivate and reactivate on save failure. Persistent reminders vs in-memory timers — [Dapr actor timers & reminders](https://docs.dapr.io/developing-applications/building-blocks/actors/actors-timers-reminders/)
- Avoid single handlers that run for hours or days; split with delayed calls so versions can drain — [Restate versioning](https://docs.restate.dev/operate/versioning)

### Inferences (concrete, cheap design for our runtime; ordered by value/cost)
1. **Run + step journal (2 tables, ~1 day of work).** `runs(id PK = idempotency key, kind, input jsonb, status, app_version, owner_node, owner_epoch, wake_at, wait_key, created_at, updated_at)` and `steps(run_id, name, seq, status, output jsonb, attempt, PRIMARY KEY(run_id, name, seq))`. A `step(name, fn)` helper returns the stored output if present, otherwise runs `fn` and inserts the output, conditional on `owner_epoch`. Expected overhead is about 1-2 ms per step, per DBOS's Postgres figures.
2. **Waits as rows, not promises.** `waitFor(key, {timeout})` sets `status='waiting', wait_key, wake_at` and returns, so the actor and process are free. The CI step becomes: dispatch the workflow, store `ci_run_id` as the step output, then `waitFor('gh:workflow_run:<id>', 3h)`. A GitHub `workflow_run` webhook, or a 1-minute poll timer as fallback, resolves it by key. This is the Temporal async-completion / Hatchet WaitForEvent / CF "job ID + hibernate" pattern, and it turns the 90-minute wait into zero held resources and deploy-safe.
3. **Durable timers via one scheduler loop.** Each node polls `SELECT ... WHERE status IN ('waiting','ready') AND wake_at <= now() FOR UPDATE SKIP LOCKED LIMIT n` every second or so, and LISTEN/NOTIFY wakes it early. This is the DO "one alarm + schedule table" pattern applied cluster-wide. It replaces in-memory `setTimeout` for anything that must survive a restart.
4. **Lease + epoch fencing for multi-node.** Claiming a run increments `owner_epoch`. Every checkpoint write is `UPDATE ... WHERE id=$1 AND owner_epoch=$2`, and zero rows updated means "you lost ownership, stop". Heartbeat expiry then only decides who may claim, and correctness does not depend on a dead node noticing it is dead (Restate epoch fencing).
5. **Versioned recovery instead of a 30-minute drain.** Stamp `app_version` (git SHA, or a hash of the job-definition module) on each run. On deploy, new nodes claim only new runs and runs at compatible versions. Old nodes finish only the step they are executing, typically seconds, and exit. Waiting runs move freely, because their state is entirely in rows. For breaking changes to a job definition, either keep the old definition registered under its version (pinning, Trigger.dev/Restate style) or branch on a `patch('name')` marker row (DBOS/Temporal style).
6. **Idempotent external steps.** Wrap non-idempotent effects (GitHub release, crates.io publish) as check-then-act inside the step: `gh release view <tag>` before create, crates.io version lookup before publish. A step re-executed after a crash between "effect done" and "checkpoint written" then becomes a no-op (Inngest/DBOS guidance that steps are at-least-once).
7. **NOTIFY hygiene.** Payload is only the run ID. Send NOTIFY after commit or in a periodic batch, never per-row from a trigger on a hot table. Listeners always re-read the table, and a low-frequency poll catches anything missed (DBOS 2026).
8. **Optional: durable mailboxes for actors that matter.** Insert inbound messages to `inbox(actor_key, seq, msg)` and commit actor state plus `processed_seq` in one transaction at the end of each turn (Dapr turn-commit). Only actors whose messages must not be lost (release, approval, billing) need this. Ephemeral chatter can stay in memory.
9. **Retention.** Delete or archive completed runs and steps after N days, since graphile-worker and Dapr both warn about table growth hurting performance.

What is not cheap and probably not worth copying: Temporal-style full deterministic replay of arbitrary workflow code (determinism linting, patch APIs everywhere), Restate's own replicated log, and Trigger.dev's CRIU process snapshots, which need CRIU-capable infrastructure and are not available self-hosted per the v4 GA page.

### Gaps
- No source measures LISTEN/NOTIFY + heartbeat clusters at our small scale (a few nodes, low write rate). The DBOS findings are about high-rate streams, and applying them to our case is an inference.
- No source was found comparing "drain-based" deploys (our 30-minute drain) with "suspend-and-resume" deploys in quantitative terms such as lost work or deploy duration. The recommendation above rests on the mechanisms, not on a measured comparison.
