# JVM/.NET actor platforms (Akka, Akka SDK / Agentic Platform, Apache Pekko, Microsoft Orleans, Akka.NET, Proto.Actor) vs the Queen BEAM-style Bun runtime

Scope note: research date 2026-10-09. Primary docs fetched: learn.microsoft.com (Orleans docs dated 2026-01..2026-07, default moniker Orleans 10.0), doc.akka.io (Akka core 2.10.24 "current"), akka.io blog, Orleans GitHub releases (10.1-10.4), the original Orleans MSR-TR-2014-41 PDF (text extracted locally). Older material is flagged inline. Our runtime for comparison: TypeScript/Bun, pids, bounded mailboxes that drop when full, control lane, monitors, supervisors with backoff, per-turn timeouts that abandon stuck turns, reduction-like slices, thread/process isolation, multi-node via Postgres LISTEN/NOTIFY + heartbeats/TTL + remote monitors, NO persistence of actor state/mailboxes across deploys, ~30 min drain on deploy.

## Q1. Virtual actors (Orleans grains): activation, passivation, location transparency, single activation, placement, live migration, persistence across deploys, timers vs reminders

### Takeaway
Orleans' core trick is that an actor (grain) is addressed by a stable `type/key` identity that "always exists"; the runtime activates it on first message, collects it when idle (15 min default) or under memory pressure, re-creates it on another silo after a crash, loads its declared persistent state before `OnActivateAsync`, and (since 7.2/8.0) can move a live activation with its in-memory state between silos. Durable periodic work survives deploys via storage-backed reminders (minutes+ granularity) while timers are per-activation and die with it. This is the single biggest mechanism class our runtime lacks: we have pids bound to a process lifetime, Orleans has identities whose lifetime is decoupled from any host.

### Cited Findings
Model and semantics (original paper, 2014 - old but still the conceptual basis):
- Four facets of virtualization: (1) perpetual existence - an actor "cannot be explicitly created or destroyed" and is unaffected by server failure; (2) automatic instantiation - the runtime creates an "activation" on a chosen server when a request arrives and none exists; (3) location transparency; (4) automatic scale-out via "single activation" (default) or "stateless worker" mode (many independent activations up to a limit) — [Orleans MSR-TR-2014-41](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/Orleans-MSR-TR-2014-41.pdf)
- The paper states Orleans "has no need for supervision trees as in Erlang and Akka", because a failed actor is re-instantiated on a new server on its next invocation; idle actors (or actors on a server under memory pressure) are deactivated locally with no distributed GC — [Orleans MSR-TR-2014-41](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/Orleans-MSR-TR-2014-41.pdf)
- Original single-activation semantics were "eventual": in failure-free times one activation, but during membership flux two activations could be registered in different directory partitions; once membership settles one is dropped. Explicit trade of availability over consistency — [Orleans MSR-TR-2014-41](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/Orleans-MSR-TR-2014-41.pdf)
- Messaging in the paper: at-least-once delivery by resending unacknowledged messages after a timeout; exactly-once rejected as too costly; FIFO between actor pairs was originally implemented and then removed because per-pair state is O(n^2) — [Orleans MSR-TR-2014-41](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/Orleans-MSR-TR-2014-41.pdf). NOTE: current `MessagingOptions.ResendOnTimeout` "Default is false", i.e. at-least-once resend is now opt-in — [SiloMessagingOptions API](https://learn.microsoft.com/en-us/dotnet/api/orleans.configuration.silomessagingoptions)
- Directory cache entry ~80 bytes per single-activation actor, "comfortably cache millions of entries"; production membership convergence configured to 30-60 s; a server declared dead shuts itself down even if the failure was a transient network issue — [Orleans MSR-TR-2014-41](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/Orleans-MSR-TR-2014-41.pdf)

Directory / single activation today:
- Orleans 9.0 replaced the eventually consistent DHT directory with a strongly consistent one "based on the two-phase Virtually Synchronous methodology", still a DHT but with virtual nodes for load balancing; lookups are cached per silo; directory is configurable per grain type — [Grain directory docs](https://learn.microsoft.com/en-us/dotnet/orleans/implementation/grain-directory)
- 9.2 added a database-backed (ADO.NET) grain directory option — [Orleans 9.2.0 release notes](https://newreleases.io/project/github/dotnet/orleans/release/v9.2.0)
- 10.3.0: "Distributed-directory rolling upgrades now have durable handoffs, cancellation-aware operations, stronger single-activation guarantees" — [Orleans 10.3.0 release notes](https://newreleases.io/project/github/dotnet/orleans/release/v10.3.0); 10.2.0 fixed activation/deactivation races, directory transfer batching, stale cache invalidation, rolling-upgrade compatibility; 10.4.0 "stronger cluster membership consistency across many storage and clustering providers" — [Orleans GitHub releases](https://github.com/dotnet/orleans/releases) (release dates shown as 12 Jun / 27 Aug / 03 Oct without year; given 10.1 in April and today's date these are 2026 - inference)
- Orleans 9 migration notes: "Faster membership protocol: Default failure detection time reduced from 10 minutes to 90 seconds" (as stated by the doc) — [Orleans migration guide](https://learn.microsoft.com/en-us/dotnet/orleans/migration-guide)

Passivation / activation collection:
- `GrainCollectionOptions.CollectionAge` default 15 minutes idle before eligible; `CollectionQuantum` 1 minute — [Grain lifecycle docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-lifecycle)
- Memory-based activation shedding (Orleans 9+): `EnableActivationSheddingOnMemoryPressure` (default false), starts at `MemoryUsageLimitPercentage` 80, sheds down to `MemoryUsageTargetPercentage` 75, polled every 5 s, deactivating older/less-recently-used grains first — [Grain lifecycle docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-lifecycle)
- Grain lifecycle stages: `SetupState` (1000, persistent state loaded if `RecordExists`) then `Activate` (2000, `OnActivateAsync`); lifecycle is NOT guaranteed to run on silo crash, so apps "shouldn't rely on the grain lifecycle always executing during grain deactivations" — [Grain lifecycle docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-lifecycle); similarly relying on `OnDeactivateAsync` "to perform important actions, such as persisting critical state, isn't recommended" — [Orleans migration guide](https://learn.microsoft.com/en-us/dotnet/orleans/migration-guide)
- Concurrency: grains are single-threaded and non-reentrant by default; opt-ins `[Reentrant]`, `[AlwaysInterleave]`, `[ReadOnly]`, and call-chain reentrancy via `RequestContext.AllowCallChainReentrancy()` to avoid A->B->A deadlocks — [Orleans migration guide](https://learn.microsoft.com/en-us/dotnet/orleans/migration-guide)

Placement strategies:
- Since 9.2 default is ResourceOptimized (was Random): weighted normalized score with defaults CpuUsageWeight 40, MemoryUsageWeight 20, AvailableMemoryWeight 20, MaxAvailableMemoryWeight 5, ActivationCountWeight 15, LocalSiloPreferenceMargin 5 (recommended 5-10); signal smoothed by a Kalman-filter-based adaptive algorithm to avoid saturating newly joined silos — [Grain placement docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-placement)
- Others: Random (good default for >= 10,000 grains), PreferLocal, HashBased (not stable across membership changes, but grains are registered in the directory so little effect), ActivationCountBased (power-of-two-choices, 2 random silos sampled by default), StatelessWorker (multiple local activations, not registered in directory), SiloRoleBased; custom `IPlacementDirector`; 9.x+ placement filtering by silo metadata (zone-aware, tiered, hardware affinity) — [Grain placement docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-placement)

Live migration / rebalancing:
- Live grain migration (7.2 line, carried into 8.0; NuGet 8.0.0 dated 2024-01-05) "allows grains to move from one silo to another without dropping requests or losing in-memory state"; used to offload existing silos when a new silo joins, and to rebalance after a rolling upgrade where "Silos upgrading early in the cycle will have substantially more grain activations than those near the end" — [What's new in Orleans 8 (devblogs, May 2024)](https://devblogs.microsoft.com/dotnet/whats-new-in-orleans-8/)
- Mechanism: dehydrate on source (after `OnDeactivateAsync`), transfer, rehydrate on target before `OnActivateAsync`; grains opt in via `IGrainMigrationParticipant` (`OnDehydrate`/`OnRehydrate` with key/value contexts) or automatically when using `IPersistentState<T>`/`Grain<T>`; triggers: `this.MigrateOnIdle()` (optionally with a placement hint target silo), the activation repartitioner, the activation rebalancer; `[Immovable]` blocks automatic (not user) migration; client grains, system targets, grain services and stateless workers cannot migrate — [Grain lifecycle docs (Grain migration section)](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-lifecycle); [IGrainMigrationParticipant API](https://learn.microsoft.com/pl-pl/dotnet/api/orleans.runtime.igrainmigrationparticipant?view=orleans-8.0)
- Activation repartitioning (experimental since 8.2, ORLEANSEXP001): tracks heaviest grain-to-grain call edges with a probabilistic structure (MaxEdgeCount 10,000; MaxUnprocessedEdges 100,000), runs rounds every 1-2 min (RecoveryPeriod 1 min), migrates grains toward their call partners while keeping activation counts balanced; docs advise against it on 2-3 silo clusters — [Grain placement docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-placement)
- Activation rebalancing (experimental, Orleans 10.0, ORLEANSEXP002): a singleton grain computes cluster "entropy" over memory usage and activation counts, then instructs heavy silos to migrate activations to light ones in sessions (RebalancerDueTime 60 s, SessionCyclePeriod 15 s, MaxStagnantCycles 3, ActivationMigrationCountLimit unlimited); needs >= 2 silos — [Grain placement docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-placement)

State across deploys (persistence):
- Grains declare named `IPersistentState<T>` slots, each bound to a named provider; state "automatically reads when the grain activates", writes are explicit via `WriteStateAsync()`; read failure fails the activation (caller gets the fault); providers set an opaque ETag and must fault writes with `InconsistentStateException` on ETag conflict (optimistic concurrency) — [Grain persistence docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-persistence/)
- Official providers: ADO.NET (SQL databases), Azure Table/Blob, Cosmos DB, DynamoDB, Redis; default storage serializer JSON for version tolerance; Redis `EntryExpiry` warned it "can cause duplicate activations" — [Grain persistence docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-persistence/)
- 10.1.0 added ADO.NET persistence support for SQLite — [Orleans GitHub releases](https://github.com/dotnet/orleans/releases)
- New in 10.x (PREVIEW, still `10.4.0-alpha.1`): `Orleans.Journaling` (pluggable grain persistence "built on replicated state", JSON Lines default format since 10.2, providers incl. Azure Table, Redis, S3 Express One Zone) and `Orleans.DurableJobs` (one-shot future jobs with at-least-once execution, survive deactivation/restarts, distributed across silos, retries, cancellation; reminders remain the recurring mechanism) — [Orleans 10.4.0 release notes](https://newreleases.io/project/github/dotnet/orleans/release/v10.4.0); [Microsoft.Orleans.DurableJobs on NuGet](https://feed.nuget.org/packages/Microsoft.Orleans.DurableJobs); [Microsoft.Orleans.Journaling on NuGet](https://packages.nuget.org/packages/Microsoft.Orleans.Journaling/)

Timers vs reminders:
- Timers: per activation, stop on deactivation or silo crash; `RegisterGrainTimer` (8.2+) options `Interleave` (default false: callbacks run as grain turns, not interleaved) and `KeepAlive` (default false: timer ticks do NOT keep an idle grain alive); period measured from callback completion so ticks never overlap; callbacks get a CancellationToken cancelled on deactivation; subject to call filters and visible in tracing — [Timers and reminders docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/timers-and-reminders)
- Reminders: definitions persisted (Azure Table, ADO.NET, Redis, Cosmos; in-memory for dev only), tied to the grain not the activation, re-activate the grain when they fire, survive partial/full cluster restarts; individual ticks are NOT stored, so a tick due while the cluster is down is skipped; delivered as normal grain messages; period should be "minutes, hours, or days"; recommended pattern: a 5-minute reminder that restarts a fine-grained local timer lost to deactivation — [Timers and reminders docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/timers-and-reminders)

Production evidence:
- Halo 4 (2012) built all its cloud services on Orleans (presence, statistics, challenges, cheater detection) — [Microsoft Research](https://www.microsoft.com/en-us/research/orleans-simplifies-development-scalable-apps-cloud/)
- Lab test of production Halo 4 Presence code: 1 million actors, 25 servers ~130,000 heartbeats/s (~5,200/server) at 95-97% CPU, scaling "almost linearly" to 125 servers; throughput nearly flat from 2 thousand to 2 million actors; load tests ran 25 servers "for many days at 90+% CPU utilization without any instability"; deep-copy isolation cost ~4% throughput for byte[] and <10% for a dictionary — [Orleans MSR-TR-2014-41](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/Orleans-MSR-TR-2014-41.pdf) (2014; lab numbers - the paper says production figures were confidential)
- Halo 4 scale: 11.6 million players, 1.5 billion games, 270 million hours by June 2013 — [QCon London 2015 talk](https://qconlondon.com/london-2015/node/2559.html); "sustainably run above 90% CPU" with near-linear scaling — [InfoQ 2015](https://www.infoq.com/news/2015/03/halo4-actor-model/)

### Inferences
- Gap vs our runtime: we tie actor identity to a pid that dies with the process; Orleans ties it to a durable key. Adding a "grain id -> current pid" directory (we already have Postgres) plus activate-on-first-message would turn a deploy from "drain 30 min" into "deactivate idle grains, let next message re-activate on a new node". The persisted-state contract (load before first turn, explicit write, ETag CAS) maps naturally to a Postgres row with a version column.
- Orleans spent a decade moving from "eventual single activation" (2014) to a strongly consistent directory (9.0, 2024) and durable directory handoff during rolling upgrades (10.3, 2026). A Postgres-backed registry with TTL leases would give us single activation by construction (row lock / unique constraint), but heartbeats/TTL mean a partitioned node can still run a stale activation until its lease expires; Orleans' answer is ETag CAS on the state write, which we would also need.
- Orleans has no supervisors by design; their "restart" is re-activation on next message. Our supervisors + backoff remain useful for long-lived service actors, but per-entity actors (sessions, issues, PRs) would be simpler as virtual actors.
- Reminders vs timers maps directly onto a gap: our timers live in memory and vanish on deploy. A Postgres-backed reminder table (definition only, minutes granularity, tick re-activates the grain) is cheap and solves "cron for actors across deploys"; Durable Jobs is the one-shot variant.
- Live migration (dehydrate/rehydrate with key/value context) is a cheaper alternative to full persistence for deploys: on SIGTERM, dehydrate idle actors, hand them to a peer, rehydrate there.

### Gaps
- Could not fetch a dedicated Orleans "grain migration" page (404); content comes from the lifecycle page and the Orleans 8 blog. Whether a silo shutting down automatically migrates (vs deactivates) its grains is not stated in any source I read.
- Orleans 9.0 / 10.0 GA dates and any official 9.0 announcement blog not retrieved; no current production-scale numbers for Orleans (post-2015) found in primary sources.
- Default values of `MaxEnqueuedRequestsHardLimit`, `MaxRequestProcessingTime`, `ResponseTimeout` were not visible on the API page (only names/descriptions).

## Q2. Akka Cluster Sharding, Cluster Singleton, Split Brain Resolver + leases, Akka Persistence, Distributed Data, Reliable Delivery

### Takeaway
Akka gives the same "entity by id" capability as Orleans but as explicit building blocks: Sharding (entity id -> shard -> node, coordinator-driven allocation and rebalancing, passivation, optional remember-entities), Singleton (oldest node), SBR (decides which side of a partition survives, with optional Kubernetes lease), Persistence (event sourcing with single-writer guaranteed by Sharding+SBR), Distributed Data (CRDTs over gossip), and Reliable Delivery (at-least-once with flow control, still flagged "may change"). The key lesson: single-writer per entity is only safe if downing is correct, which is why SBR exists.

### Cited Findings
Cluster Sharding:
- Entities grouped into shards; default shard id = abs(entityId.hashCode) mod number-of-shards; `akka.cluster.sharding.number-of-shards` default 1000 and must match on all nodes (changing it requires a full cluster stop); recommended ~10x the planned max node count — [Cluster Sharding docs](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)
- Coordinator state store default `ddata` (WriteMajorityPlus/ReadMajorityPlus), in-memory replicated, lost when all nodes stop; `persistence` mode deprecated — [Cluster Sharding docs](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)
- Rebalancing: `LeastShardAllocationStrategy`, check every `rebalance-interval` 10 s; newer algorithm enabled by `rebalance-absolute-limit` > 0 (default 0 for compatibility, recommended to enable); `handoff-timeout` 60 s, entities not stopping within (handoff-timeout - 5 s) are stopped forcibly; docs warn Kubernetes' default 30 s SIGTERM->SIGKILL gap can be shorter than the handoff timeout — [Cluster Sharding docs](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)
- In-flight buffering: ShardRegion buffers up to `buffer-size` 100000 messages while a shard's location is unknown / being handed off; on passivation, the shard buffers incoming messages until the entity terminates then delivers them to a new incarnation — [Cluster Sharding docs](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)
- Passivation: legacy default idle timeout 2 minutes; recommended `default-strategy` caps active entities (example 1,000,000 per region) using segmented LRU + W-TinyLFU admission (window 1% of limit, hill-climbing adaptation) — [Cluster Sharding docs](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)
- Remember entities: off by default; when on, moved/recovered shards re-create their entities; stores `ddata` (LMDB on disk) or `eventsourced`; disables automatic passivation; `entity-restart-backoff` 10 s — [Cluster Sharding docs](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)
- Per-shard leases: `use-lease` (empty by default) makes each shard acquire lease `<system>-shard-<type>-<shardId>`; a shard that cannot acquire stays uninitialized and its messages are buffered; losing the lease terminates the shard; `lease-retry-interval` 5 s. Other timers: shard-start-timeout 10 s, coordinator-failure-backoff 5 s, retry-interval 2 s — [Cluster Sharding docs](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)
- External shard allocation (via DData LWWMap) and co-location (`ConsistentHashingShardAllocationStrategy`) are supported — [Cluster Sharding docs](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)

Split Brain Resolver and leases:
- Strategies: keep-majority (default), static-quorum, keep-oldest (follows the singleton; a 2-node side can beat a 98-node side), down-all (not for > 10 nodes), lease-majority (only the side holding a Kubernetes CRD lease survives; minority waits `acquire-lease-delay-for-minority` 2 s; `release-after` 40 s; no lease -> all nodes downed) — [SBR docs](https://doc.akka.io/libraries/akka-core/current/split-brain-resolver.html)
- `stable-after` default 20 s (recommended 7 s at 5 nodes up to 30 s at 1000 nodes); `down-all-when-unstable` on (3/4 of stable-after); indirectly connected nodes are downed, but if that would down >= half (`down-all-when-indirectly-connected` 0.5) all nodes are downed; expected default failover ~45 s (5 s detection + 20 s stable-after + 20 s down-removal-margin) — [SBR docs](https://doc.akka.io/libraries/akka-core/current/split-brain-resolver.html)
- Why: a crash and a partition look identical; timeout-based removal on both sides creates two clusters, and with Sharding/Singleton two persistent actors could write the same event stream "with fatal consequences on replay"; "unreachable" is an observation, "down" is a decision; Akka does not auto-down unreachable nodes by default — [SBR docs](https://doc.akka.io/libraries/akka-core/current/split-brain-resolver.html)

Cluster Singleton:
- Singletons always run on the oldest node; during rollouts "upgrade the oldest node last" so the singleton moves once — [Rolling updates docs](https://doc.akka.io/libraries/akka-core/current/additional/rolling-updates.html)

Akka Persistence (event sourcing):
- Command handler returns an `Effect` (persist/none/unhandled/stop/stash/reply); event handler computes state and must be side-effect free; `thenRun` side effects are at-most-once and skipped if persist fails; multi-event `persist` is atomic or rejected — [Persistence docs](https://doc.akka.io/libraries/akka-core/current/typed/persistence.html)
- Single writer: "For a particular persistenceId only one persistent actor instance should be active at one time"; "Cluster Sharding ensures that there is only one active entity for each id" — [Persistence docs](https://doc.akka.io/libraries/akka-core/current/typed/persistence.html)
- Recovery replays events (optionally from a snapshot); commands are stashed during recovery and during in-flight persists; `akka.persistence.max-concurrent-recoveries = 50`; `Recovery.replayOnlyLast` only on R2DBC; replay filter modes repair-by-discard-old/fail/warn/off; on journal failure the actor stops by default, or `onPersistFailure` with backoff (plain resume is invalid since it is unknown whether the event was stored) — [Persistence docs](https://doc.akka.io/libraries/akka-core/current/typed/persistence.html)

Distributed Data (CRDTs):
- Replicator-actor KV store of CRDTs (GCounter, PNCounter, GSet, ORSet, ORMap, ORMultiMap, LWWMap, PNCounterMap, LWWRegister, Flag) spread by direct replication + gossip; consistency levels WriteLocal/WriteTo(n)/WriteMajority/WriteMajorityPlus/WriteAll and matching reads, with (nodes_written + nodes_read) > N for read-your-writes; in-memory by default, optional LMDB durability; "The number of top level entries should not exceed 100000"; delta-CRDTs on by default (max-delta-size 50); gossip-interval 2 s, subscriber notify 500 ms — [Distributed Data docs](https://doc.akka.io/libraries/akka-core/current/typed/distributed-data.html)

Reliable Delivery:
- Point-to-point, work-pulling (workers registered via Receptionist), and sharding variants; consumer-driven flow control (producer never exceeds demand; window-bounded unconfirmed messages); effectively-once in order without crashes, at-least-once (duplicates) on crash/rebalance; durable producer via `EventSourcedProducerQueue` with "substantial performance overhead"; chunking of large messages only point-to-point; module is "may change" and "not recommended to use this module in production just yet" (still stated in the 2.10.24 docs) — [Reliable Delivery docs](https://doc.akka.io/libraries/akka-core/current/typed/reliable-delivery.html)

### Inferences
- Our Postgres LISTEN/NOTIFY + heartbeat/TTL membership has no equivalent of SBR: if two nodes disagree on who is alive, nothing guarantees a single owner for an entity. Akka's lease-majority strategy (lease in an external store, minority waits then yields) is directly implementable with a Postgres advisory lock or lease row - we already have the store.
- Akka's sharding numbers are a useful template for an "entity -> node" layer on top of our pids: fixed shard count (~10x nodes), coordinator singleton, buffer-during-handoff (100k), handoff timeout (60 s) that must be < platform kill grace. Our 30-minute drain suggests we lack handoff entirely: with handoff, a node can leave in roughly one handoff-timeout.
- Akka's persistence lesson for us: persistence without single-writer enforcement is dangerous; adding state persistence should come together with (a) an owner lease per entity and (b) a sequence number / ETag CAS on writes.
- Reliable Delivery's still-experimental status after ~5 years is evidence that general at-least-once actor messaging is hard to productize; Orleans also made resend opt-in. Our "drop when full" is in line with the default at-most-once stance of both platforms.

### Gaps
- Sharded Daemon Process (keep N workers alive across the cluster) and Cluster Singleton detailed config were not fetched.
- Snapshot retention defaults (`RetentionCriteria.snapshotEvery`, `keepNSnapshots`), default stash capacity, and Replicated Event Sourcing details were in truncated parts of the persistence page.
- No production failure statistics (e.g., split-brain incident rates) found from primary sources.

## Q3. Backpressure and flow control (Akka Streams, bounded/priority mailboxes, stash; Orleans equivalents)

### Takeaway
Akka offers three tiers: (1) Akka Streams with Reactive Streams demand-based, non-blocking backpressure; (2) per-actor mailbox choices including bounded (overflow to dead letters), control-aware (control messages jump the queue - the same idea as our control lane) and stable priority mailboxes; (3) stash for deferring messages during state transitions (used automatically by Persistence). Orleans instead rejects requests above a per-grain queue limit, sheds load on CPU threshold, and only reports (does not abort) stuck requests. Our runtime already has bounded drop-when-full mailboxes and a control lane; what we lack is demand signalling to producers and caller-visible rejection.

### Cited Findings
- Akka Streams implements Reactive Streams backpressure, "always understood as non-blocking and asynchronous": subscribers signal demand via `Request(n)`, sources never emit beyond total demand; "dynamic push/pull mode"; operators are fused by default into one actor (one core per fused segment), `async` boundaries add parallelism; explicit `buffer` operators take overflow strategies — [Akka Streams basics](https://doc.akka.io/libraries/akka-core/current/stream/stream-flows-and-basics.html)
- Default actor mailbox is unbounded (`SingleConsumerOnlyUnboundedMailbox`); `BoundedMailbox` blocks senders only with a non-zero `mailbox-push-timeout-time` (docs advise zero); `NonBlockingBoundedMailbox` discards overflow to dead letters; `UnboundedControlAwareMailbox` / `BoundedControlAwareMailbox` deliver `ControlMessage`s first; `UnboundedStablePriorityMailbox` keeps FIFO within equal priority; typed selection via `MailboxSelector.bounded(capacity)` — [Akka mailboxes docs](https://doc.akka.io/libraries/akka-core/current/typed/mailboxes.html)
- Stash: Persistence stashes incoming commands automatically during recovery and while a persist is in flight; explicit `stash`/`unstashAll` effects exist — [Persistence docs](https://doc.akka.io/libraries/akka-core/current/typed/persistence.html)
- Reliable Delivery adds consumer-driven demand windows between actors (producer never sends faster than consumer demand) — [Reliable Delivery docs](https://doc.akka.io/libraries/akka-core/current/typed/reliable-delivery.html)
- Orleans: `MaxEnqueuedRequestsHardLimit` - "per grain threshold for pending requests. Requests are rejected when exceeded" (soft limit only warns; separate limits for stateless workers); `MaxRequestProcessingTime` - "maximum time that a request can take before the activation is reported as 'blocked'"; `RequestProcessingWarningTime`, `RequestQueueDelayWarningTime`; `DropExpiredMessages` drops messages that time out before delivery; `MaxForwardCount` bounds re-forwarding during membership instability — [SiloMessagingOptions API](https://learn.microsoft.com/en-us/dotnet/api/orleans.configuration.silomessagingoptions)
- Orleans 10: `CancelRequestOnTimeout` default changed from true to false (no cancellation message sent on caller timeout unless enabled); `LoadSheddingOptions.CpuThreshold` (renamed from LoadSheddingLimit; example 95) — [Orleans migration guide](https://learn.microsoft.com/en-us/dotnet/orleans/migration-guide)
- Orleans 9 added full `CancellationToken` support on grain methods; 10.4 flows trailing cancellation tokens through runtime, reminder, streaming and transaction APIs — [Orleans migration guide](https://learn.microsoft.com/en-us/dotnet/orleans/migration-guide); [Orleans GitHub releases](https://github.com/dotnet/orleans/releases)
- Akka.NET 1.6 plans Akka.Streams-based backpressure inside the remoting transport so buffers do not flood, plus a separate system-message lane that works even while a node is quarantined — [Petabridge v1.6 roadmap](https://petabridge.com/blog/akkadotnet-v1.6-roadmap/)

### Inferences
- Our "control lane" equals Akka's ControlAwareMailbox; our "drop when full" equals NonBlockingBoundedMailbox (to dead letters). Neither platform silently drops on a request/response call: Orleans rejects with an error to the caller. A caller-visible "mailbox full" reply (or dead-letter event) would make drops observable.
- Our per-turn timeout that abandons the turn is stronger than Orleans (which only reports "blocked") and closer to BEAM's kill semantics; Orleans relies on cooperative CancellationToken flow instead. Worth noting as a differentiator, but abandoning a turn without cancellation propagation can leave half-done side effects - Orleans' 9/10 investment in end-to-end cancellation is the mitigation pattern.
- Demand-driven flow (Request(n)) between producer actors and slow consumers (LLM calls, GitHub API) is the main backpressure mechanism we lack.

### Gaps
- Akka Streams default internal buffer sizes and the list of overflow strategies were not on the fetched page.
- Default numeric values for Orleans enqueued-request limits and request timeouts were not visible.

## Q4. Rolling / zero-downtime deploys: version skew and in-flight messages

### Takeaway
Both platforms treat rolling updates as a first-class, documented procedure: compatible serialization in both directions, a cluster-visible app version that steers new allocations to new nodes, graceful leave that hands off shards/singletons, and an explicit list of changes that need a full restart. Orleans adds per-interface grain versioning (old and new silos coexist; incompatible activations are re-created on compatible silos) and live migration to rebalance after the roll. Neither requires a 30-minute drain; Akka's per-shard handoff is bounded by a 60 s timeout.

### Cited Findings
Akka:
- Serialization must be compatible both ways during a roll (old nodes read new messages/events and vice versa); a `NotSerializableException` in `fromBinary` is treated as transient (logged, message dropped) while other exceptions break the connection; multi-step procedures documented for serializer migration (e.g., Java serialization -> Jackson in 4 rolling steps) — [Rolling updates docs](https://doc.akka.io/libraries/akka-core/current/additional/rolling-updates.html)
- `akka.cluster.app-version` (bump per roll; can be derived from the Kubernetes `deployment.kubernetes.io/revision` annotation via Akka Management): LeastShardAllocationStrategy stops allocating shards to old-version nodes, "Rebalance is disabled during rolling updates", shards from stopped nodes move when messages arrive — [Rolling updates docs](https://doc.akka.io/libraries/akka-core/current/additional/rolling-updates.html)
- Graceful leave via Coordinated Shutdown on SIGTERM (sharding and singleton handoff happen automatically); readiness check delays traffic until Sharding is initialized; Akka Management's Kubernetes Rolling Updates feature controls pod deletion order — [Rolling updates docs](https://doc.akka.io/libraries/akka-core/current/additional/rolling-updates.html)
- Changes requiring full shutdown: changing `extractShardId`, shard region role, persistence mode, `number-of-shards`, SBR strategy, remoting transport (classic -> Artery) — [Rolling updates docs](https://doc.akka.io/libraries/akka-core/current/additional/rolling-updates.html)
- In-flight messages: ShardRegion buffers up to 100000 messages during handoff; `handoff-timeout` 60 s; K8s default 30 s grace may cut handoff short — [Cluster Sharding docs](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)

Orleans:
- Grain interface versioning: `[Version(X)]` on interfaces (default 0); default compatibility is backward-compatible only (v1 caller -> v2 grain OK, not the reverse); if an existing activation is incompatible with a caller, Orleans deactivates it and creates a compatible one; when versions coexist new activations go randomly to compatible silos; strategies set via `GrainVersioningOptions` (`DefaultCompatibilityStrategy`, `DefaultVersionSelectorStrategy` e.g. MinimumVersion); not supported for stateless workers or streaming interfaces — [Grain versioning docs](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-versioning/grain-versioning)
- Orleans 7.0 broke the wire protocol (string grain ids + version-tolerant serializer, "up to 170% higher end-to-end throughput"), so 3.x -> 7.0 required a new cluster; 7.x -> 10.0 rolling upgrades are "not recommended" (deploy a new cluster, migrate state, switch traffic) — [Orleans migration guide](https://learn.microsoft.com/en-us/dotnet/orleans/migration-guide)
- Version-tolerant serialization and `[Alias]`/`GrainTypeAttribute` allow renaming types without breaking deployments; streaming partition count "DO NOT CHANGE ... if you do rolling deployment" — [Orleans migration guide](https://learn.microsoft.com/en-us/dotnet/orleans/migration-guide)
- After a rolling upgrade, early-upgraded silos hold more activations; live migration rebalances them — [What's new in Orleans 8](https://devblogs.microsoft.com/dotnet/whats-new-in-orleans-8/)
- `ShutdownRerouteTimeout`: "the period of time the silo will wait to reroute queued messages before it continues shutting down" (marked obsolete in 10.0); 10.3 added durable directory handoffs for rolling upgrades — [SiloMessagingOptions API](https://learn.microsoft.com/en-us/dotnet/api/orleans.configuration.silomessagingoptions); [Orleans 10.3.0 release notes](https://newreleases.io/project/github/dotnet/orleans/release/v10.3.0)
- 10.4.0 upgrade caution: interfaces with `[Id]` on parameters or non-trailing cancellation tokens may have argument wire IDs renumbered when moving off 10.3.1, so clients and silos should be upgraded together - i.e. even minor releases can carry version-skew hazards — [Orleans 10.4.0 release notes](https://newreleases.io/project/github/dotnet/orleans/release/v10.4.0)

### Inferences
- Our ~30-minute drain is the cost of not having (a) movable identities and (b) handoff. The minimal Akka-style recipe for us: publish `app_version` per node in the Postgres membership table; stop placing new entities on old-version nodes; on SIGTERM, for each entity actor either persist+stop (re-activate elsewhere on next message) or dehydrate+transfer; bound the whole thing by a handoff timeout shorter than the platform kill grace.
- A message-schema version on every envelope plus "backward compatible only" rules (new can read old) is what both platforms rely on; we should treat a NotSerializable-equivalent decode failure as drop+log rather than crash, as Akka does.
- Durable mailboxes are NOT how either platform survives deploys; they survive via persisted entity state + caller retries + bounded handoff buffers. That suggests persisting mailboxes is lower priority than persisting entity state.

### Gaps
- No primary-source numbers on actual rollout duration or message loss rates during Akka/Orleans rolling deploys in production.
- Whether Orleans silo shutdown migrates live grains automatically (vs deactivating them) is not documented in fetched sources.

## Q5. Akka Agentic Platform / Akka SDK (2024-2026): agents as durable entities, memory, workflows, streaming, evals; published numbers

### Takeaway
Akka repositioned itself (Lightbend renamed to Akka, Nov 2024) around the Akka SDK (higher-level components on top of the actor libraries) and in July 2025 launched the Akka Agentic Platform: Agents, Orchestration (durable workflows), Memory (event-sourced, sharded session memory), Streaming, plus later an evaluation console. The concrete mechanisms are: an Agent component bound to a session id whose memory is a regular Event Sourced Entity; Workflows for multi-agent orchestration that survive crashes; typed failure handling for model/tool errors. Published numbers are vendor claims (1B tokens/s largest deployment, 1.4M TPS benchmark, "3x velocity, 1/3 compute"), not independently verified.

### Cited Findings
- Akka 3 launched 2024-11-15 with Lightbend renaming itself Akka: SDK components with local console/debugger, Serverless and Bring-Your-Own-Cloud environments; "writable conflict-free replicated data types (CRDT) running globally" (multi-master, multi-region), replication across clouds/regions for no-downtime migrations and DR — [Akka 3 press release](https://akka.io/blog/lightbend-launches-akka-3-rebrands-company-as-akka); [Announcing Akka 3](https://akka.io/blog/announcing-akka-3); heise describes the mechanism as replicated event logging over gRPC — [heise](https://heise.de/-10048204)

- Akka Agentic Platform announced July 2025 (blog dated July 11, press July 14): Akka Orchestration (long-running multi-agent systems "even across crashes, delays, or infrastructure failures"; sequential, parallel, hierarchical, human-in-the-loop; registry of agents/tools/APIs), Akka Agents (goal-directed agents, MCP tools, HTTP/gRPC APIs), Akka Memory ("durable, in-memory, sharded" short- and long-term memory), Akka Streaming (continuous processing of live data, audio, video; ingest e.g. Kafka); Agent Testkit; evaluation console (tracing, auditing, debugging, eval with performance/functional/cost traces) slated for a later release; included in existing customer licenses — [Announcing the Akka Agentic Platform](https://akka.io/blog/announcing-akkas-agentic-ai-release)

- Failure handling: `onFailure` on the agent effect, typed exceptions `ModelException`, `RateLimitException`, `ModelTimeoutException`, `ToolCallExecutionException`, `McpToolCallExecutionException`, `ToolCallLimitReachedException`, `JsonParsingException` — [Akka SDK agent failures docs](https://doc.akka.io/sdk/agents/failures.html)

- Deloitte Canada partnership for agentic AI (Aug 2025) — [Akka and Deloitte press release](https://akka.io/blog/news-akka-and-deloitte)

### Inferences
- The Akka SDK's agent model is essentially "virtual actor keyed by session id + event-sourced memory + durable workflow orchestrator". For Queen, the transferable pieces are: (a) per-session durable memory as an append-only event log with compaction at a sequence number; (b) orchestration as a persisted workflow (step state checkpointed) rather than an in-memory supervisor chain, so a deploy mid-task resumes instead of restarting; (c) typed model/tool failure taxonomy (rate limit vs timeout vs tool error) feeding retry policy.
- Their headline numbers measure the runtime/data layer, not agent task success; none are independently verified. Treat as marketing, not benchmarks.

## Q6. Licensing changes and adoption trends 2025-2026 (Akka BSL, Pekko, Akka.NET, Proto.Actor, Orleans)

### Takeaway
Akka moved from Apache 2.0 to BSL 1.1 starting with 2.7 (announced 2022-09-07); I found no further license change in 2025-2026, only the Akka 3 / SDK commercial repositioning. The community answer is Apache Pekko (fork of Akka 2.6.x, ASF top-level project), adopted by Play 3.0 and listed as used by Flink; Pekko 2.0 is in milestones (M4 dated 2026-08-21). Akka.NET (.NET port, Petabridge) is working toward v1.6 (AOT, new transport). Orleans remains open source on GitHub with frequent releases (10.1-10.4 in 2026; license not re-verified here). Proto.Actor is active but thinly documented.

### Cited Findings

- For a TypeScript runtime that wants these mechanisms, Orleans' design (virtual actors + pluggable persistence/reminders/directory over an SQL store) is the closest conceptual fit to our Postgres-centered multi-node design, and its public docs and source can be studied freely; Akka's newer ideas are behind BSL (ideas are not licensed, code is).
