# Agent frameworks and swarm platforms on (or compared with) the actor model, 2025-2026, plus TS/JS actor libraries

Scope note: research done 2026-10-09. Most of the sources are vendor docs and vendor blogs. Measured numbers are marked as **measured**, vendor claims as **vendor claim**, and second-hand reports as **secondary**. Items older than 2026 are flagged with their date.

---

## Q1. Microsoft Agent Framework (MAF) and the AutoGen Core actor runtime: message routing, agent lifecycle, distribution

### Takeaway
AutoGen Core (0.4+) is the closest thing in the agent world to an explicit actor runtime. Agents are addressed by `AgentId(type, key)` and created lazily by a registered factory on first message. Messages go either directly to an ID or through pub/sub topics mapped to agent types by subscriptions. A gRPC host brokers messages between worker processes. Its successor, Microsoft Agent Framework 1.0 (GA April 2026), moved the centre of gravity to typed graph **workflows** with checkpoints, `RequestPort` human-in-the-loop and a Durable Task extension. In other words: durable-workflow semantics, not a hand-run actor runtime.

### Cited Findings
**Status / timeline**
- MAF 1.0 shipped for .NET and Python on 2026-04-03, billed as "the production-ready release: stable APIs, and a commitment to long-term support". The stable tier covers the single-agent abstraction, middleware hooks, memory/context providers, graph-based workflows and orchestration patterns including Magentic-One. DevUI (browser debugger) is still in preview. — [MS devblog, MAF 1.0](https://devblogs.microsoft.com/agent-framework/microsoft-agent-framework-version-1-0/); [Visual Studio Magazine, 2026-04-06](https://visualstudiomagazine.com/articles/2026/04/06/microsoft-ships-production-ready-agent-framework-1-0-for-net-and-python.aspx)
- MAF is "a single SDK + runtime for building agents and multi-agent workflows for both Python and .NET that unifies Semantic Kernel and AutoGen". It is built by the AutoGen and SK core teams, and the migration guide credits AutoGen with pioneering "GroupChat and event-driven agent runtime". — [MS Learn migration guide from AutoGen](https://learn.microsoft.com/agent-framework/migration-guide/from-autogen)
- AutoGen reportedly went into maintenance mode in October 2025 ("will not receive new features ... community managed"), with bug and security fixes only. **Secondary**: the wording came from forks and mirrors, not verified on the official repo. Sources also disagree on whether Semantic Kernel is in maintenance mode as well. — [Atlan, What is AutoGen](https://atlan.com/know/ai-agent/what-is-autogen/); [VS Magazine](https://visualstudiomagazine.com/articles/2026/04/06/microsoft-ships-production-ready-agent-framework-1-0-for-net-and-python.aspx)

**AutoGen Core actor semantics** (docs for 0.4.x, written in 2025; older but still the reference design)
- An agent ID is a `(type, key)` pair, rendered as `Agent_Type/Agent_Key`, that "uniquely identifies an agent instance within a runtime, including distributed runtime". Types come from code and keys usually from message data. Example: a `code_reviewer` type with one instance per review request, keyed by request ID. — [AutoGen docs, Agent Identity and Lifecycle](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/core-concepts/agent-identity-and-lifecycle.html)
- "Application does not create agents directly, rather, it registers an agent type with a factory function." On delivery the runtime "either fetches the instance, or creates it if it does not exist" (virtual-actor style activation). Paging instances in and out to save resources "is not implemented yet", so there is no deactivation or passivation. — [same](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/core-concepts/agent-identity-and-lifecycle.html)
- Topics and subscriptions: a subscription maps a topic to an agent type. A topic with no subscription is delivered to no one, and overlapping subscriptions still deliver once per recipient. A *type-based subscription* maps a topic type to an agent type, with the topic source becoming the agent key. A *prefix subscription* "causes each source to have its own agent instance". `publish_message()` is fire-and-forget, with no delivery confirmation. Subscriptions can be added or removed at runtime. — [AutoGen agent-runtime docs (Mintlify mirror)](https://www.mintlify.com/microsoft/autogen/core/agent-runtime); [AutoGen distributed runtime write-up](https://instagit.com/microsoft/autogen/running-autogen-agents-with-distributed-runtime-across-multiple-machines)
- Distributed runtime: `GrpcWorkerAgentRuntimeHost` is a gRPC server that "brokers messages between workers". `GrpcWorkerAgentRuntime` is a client runtime that registers local agents and runs a read loop over request, response and CloudEvent messages. The host keeps a `SubscriptionManager` keyed by client connection and drops a client's subscriptions when it disconnects. — [AutoGen 0.4.4 source, host servicer](https://microsoft.github.io/autogen/0.4.4/_modules/autogen_ext/runtimes/grpc/_worker_runtime_host_servicer.html); [instagit summary](https://instagit.com/microsoft/autogen/running-autogen-agents-with-distributed-runtime-across-multiple-machines)
- Cross-language: .NET agents declare topics with attributes, e.g. `[TypeSubscription("HelloTopic")]`, over shared gRPC contracts. — [AutoGen .NET Contracts API](https://microsoft.github.io/autogen/dotnet/dev/api/Microsoft.AutoGen.Contracts.html); [instagit cross-language](https://instagit.com/microsoft/autogen/building-cross-language-net-and-python-agent-applications)

**MAF workflows: durability and HITL**
- `RequestPort` is "a typed request/response channel between the workflow and the outside world. When an executor reaches a request port, the workflow pauses and emits an external request event". Responses are matched to handlers by type annotations. — [MS Learn, workflows human-in-the-loop](https://learn.microsoft.com/nb-no/agent-framework/workflows/human-in-the-loop)
- "Checkpointing allows workflows to save their state at specific points and resume execution later, even after process restarts." The HITL sample saves a checkpoint on every superstep-completed event. — [MS Learn, checkpointing and resuming](https://learn.microsoft.com/en-us/agent-framework/tutorials/workflows/checkpointing-and-resuming)
- **Secondary**: a checkpoint stores in-flight messages, per-executor state and `pending_request_info_events`. Resume loads the latest checkpoint and passes a `responses` dict keyed by request ID. — [instagit, durable agents in MAF](https://instagit.com/microsoft/agent-framework/how-to-implement-durable-agents-with-checkpoint-and-resume-in-agent-framework)
- The Durable Task extension adds durable execution to agents, orchestrations and workflows. It can "Pause for human input or external events without consuming compute or model tokens while waiting" and "automatically checkpoints each step in the graph". It recommends "orchestrations for imperative agent coordination with conditional logic, and workflows for fixed graph topologies with type-validated message routing". Hosting is Azure Functions or bring-your-own-compute, in C# and Python. — [MS Learn, durable extension](https://learn.microsoft.com/he-il/agent-framework/integrations/durable-extension); [Azure Durable Task, durable agents](https://learn.microsoft.com/en-us/azure/durable-task/sdks/durable-agents-microsoft-agent-framework)

### Inferences
- AutoGen's `(type, key)` addressing with "prefix subscription = one instance per source" maps directly onto "one bee actor per GitHub issue". Keying the actor by issue number makes duplicate pickup structurally impossible within one runtime. Our pid-based runtime could add a key-based registry (get-or-create by `bee/issue-1234`) on top of pids.
- AutoGen's fire-and-forget publish and silent drop of unsubscribed topics are known footguns. A dead-letter or "no subscriber" counter in our mailbox layer would surface those drops instead of losing messages quietly.
- Microsoft's direction (actor runtime → durable workflow plus checkpoint plus `RequestPort`) suggests the long-running 5-step release and the Telegram approval belong in a durable, checkpointed workflow layer *above* the actors, not inside a mailbox. The pending approval request should be persisted with an ID so a restart or redeploy does not lose it, and waiting should cost no compute.

### Gaps
- No official MAF documentation of a distributed actor runtime with topics and subscriptions was found. It is unclear whether MAF kept AutoGen's gRPC worker runtime or replaced it with Durable Task.
- No published throughput or latency numbers for the AutoGen gRPC runtime were found.
- MAF's built-in budget, rate-limit and tracing primitives were not researched in depth. OpenTelemetry support is likely but was not verified here.

## Q2. Akka, Dapr Agents, Cloudflare Agents, Ray, Letta, LangGraph, OpenAI Agents SDK, Mastra, CrewAI: isolation, durable state, scheduling, approvals, budgets, streaming, tracing

### Takeaway
Three platforms are literally actor-based: Akka (actors/entities), Dapr Agents (Dapr virtual actors beneath durable workflows) and Cloudflare Agents (each agent is a Durable Object, which is single-threaded, addressable, durable, hibernating, and alarm-scheduled). RivetKit (Q4) copies the Cloudflare model. The others (LangGraph, OpenAI Agents SDK, Mastra, CrewAI) are not actor runtimes. They converge on the same agent-specific primitives instead: a persisted run state keyed by a thread or run ID, an `interrupt`/`suspend`/`needsApproval` primitive that serialises the pending request and resumes later, and iteration or turn caps as the main budget control. Real per-agent cost budgets enforced by the runtime are rare. Akka's inline evaluation interrupting on cost thresholds is the clearest example found.

### Cited Findings
**Akka Agentic Platform** (launched 2025-07-14)
- The platform comprises orchestration, agents, memory and streaming. Akka Memory is "durable, in-memory, sharded data", with each change stored as an immutable event (audit trail). It is replicated across clusters and regions. Writes in nanoseconds and "millions of TPS" are **vendor claims**. — [Akka press release](https://akka.io/blog/news-akka-introduces-agentic-ai-platform); [Akka announcement blog](https://akka.io/blog/announcing-akkas-agentic-ai-release); [SD Times](https://sdtimes.com/ai/akka-introduces-platform-for-distributed-agentic-ai/)
- The Agent component: "stateless Agent components can run concurrently on all cluster nodes". State comes from Entity and Workflow components, and session memory "leverages Entities", which replicate across regions. User messages, tool calls and model responses are recorded into session memory automatically, which can be windowed (e.g. `readLast(5)`). The runtime sits on a "15-year hardened" actor implementation. — [Akka, Introducing the Agent component](https://akka.io/blog/introducing-akkas-new-agent-component)
- Failure handling is declarative via `onFailure`, covering rate-limit, model-timeout and tool-execution exceptions. Tokens can stream to endpoints over SSE. Inline evaluation checks inputs and outputs per call and "can interrupt the workflow on cost or quality thresholds". Orchestration supports sequential, parallel, hierarchical and human-in-the-loop patterns "even across crashes, delays, or infrastructure failures". — [same](https://akka.io/blog/introducing-akkas-new-agent-component)
- The orchestration layer uses actor supervision to change coordination flows as goals change. — [SiliconANGLE, 2025-07-14](https://siliconangle.com/2025/07/14/akka-strives-create-certainty-ai-agents-behavior-decision-making/)

**Dapr Agents** (v1.0 GA 2026-03-23, CNCF)
- A Python framework on the Dapr runtime. "Every agent invocation" runs as its own durable workflow, including agent-to-agent calls. User input, intermediate steps, tool calls and decisions are persisted, so a crash mid-LLM-call resumes from the exact state. — [CNCF announcement](https://www.cncf.io/announcements/2026/03/23/general-availability-of-dapr-agents-delivers-production-reliability-for-enterprise-ai/); [Diagrid blog](https://www.diagrid.io/blog/dapr-agents-1-0-durable-cloud-native-production-ready)
- The Workflow API "under the hood uses actors". Each agent is a virtual actor that "can be scaled to zero when idle" and keeps its state. "Thousands of agents ... on a single core machine with double-digit millisecond latency when scaling from zero" is a **vendor claim** from the project wiki. — [Dapr Agents docs](https://docs.dapr.io/developing-ai/dapr-agents/dapr-agents-introduction/); [dapr-agents wiki](https://github.com/dapr/dapr-agents/wiki)
- Adoption: >8,000 monthly PyPI downloads (**vendor claim**, Diagrid is the primary maintainer). Named user: ZEISS Vision Care. — [Diagrid](https://www.diagrid.io/blog/dapr-agents-1-0-durable-cloud-native-production-ready); [CNCF](https://www.cncf.io/announcements/2026/03/23/general-availability-of-dapr-agents-delivers-production-reliability-for-enterprise-ai/)

**Cloudflare Agents SDK**
- "Agents *are* Durable Objects": DurableObject → partyserver `Server` → `Agent`. A DO is a "single-threaded compute instance with long-term storage". Agents are addressed by name (`getAgentByName`), and `setState()` persists to SQLite and broadcasts to connected clients. Inactive DOs are evicted after 70-140 s, while WebSockets survive hibernation. `keepAlive()`/`keepAliveWhile()` prevent eviction during long work. — [Cloudflare docs, Agent class](https://developers.cloudflare.com/agents/concepts/agent-class/)
- Scheduling: "Durable Objects only allow one alarm at a time", so the SDK stores many schedules in a `cf_agents_schedules` table multiplexed onto one alarm (delayed, at-time, cron). The queue (`cf_agents_queues`) is "flushed in sequence". Default retries are 3 attempts, 100 ms base and 3000 ms max delay, applied to `schedule()`, `queue()` and `this.retry()`. `hungScheduleTimeoutSeconds` defaults to 30. — [same](https://developers.cloudflare.com/agents/concepts/agent-class/); [agents@0.24.0 scheduling doc](https://unpkg.com/agents@0.24.0/docs/scheduling.md)
- HITL can be added at the MCP layer, in durable Workflows (pause/resume for approval), or via `needsApproval` on tool calls. **Secondary**: `runFiber()`/`stash()` survive DO eviction. — [Cloudflare docs, human-in-the-loop](https://developers.cloudflare.com/agents/concepts/human-in-the-loop); [agents-sdk skill summary](https://skills.sh/midudev/autoskills/agents-sdk)

**Ray**
- Actor-level agent frameworks on Ray are mostly third-party: RayAI from Open Core Ventures (Nov 2025, since renamed SuperServe), built on Ray Serve with gVisor sandboxes for code. Ant Group's "Ragent" is reported only second-hand. — [OCV blog](https://www.opencoreventures.com/blog/rayai-extends-ray-oss-to-orchestrate-multi-agent-systems); [rayai on PyPI](https://pypi.org/project/rayai/)

**Letta (ex-MemGPT)**
- Agent state, including memory blocks, persists to Postgres or SQLite and is queryable via REST. The Agent File (`.af`) checkpoints and moves agents. Memory blocks can be shared between agents by ID. `enable_sleeptime` creates a background "sleep-time" agent that shares memory and does the memory editing for the primary agent. — [Letta, stateful agents](https://www.letta.com/blog/stateful-agents/); [Letta TS SDK](https://docs.letta.com/api/typescript); [Letta Python](https://docs.letta.com/api/python)

**LangGraph**
- `interrupt(value)` inside a node saves graph state via the checkpointer and "waits indefinitely". Resume is `Command(resume=...)`, which becomes the return value of `interrupt()`, and the pending payload surfaces as `__interrupt__`. It requires a checkpointer (durable in production) and a `thread_id`. — [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts); [LangGraph HITL](https://docs.langchain.com/oss/python/langgraph/human-in-the-loop)
- Durable execution is "enabled" whenever a checkpointer is used. Durability modes run from `"exit"` (persist only on exit, error or interrupt) upward. Critically, "Whenever execution resumes, it starts at the beginning of the node", so nodes must be deterministic and idempotent, with side effects wrapped in tasks. — [LangGraph durable execution](https://docs.langchain.com/oss/javascript/langgraph/durable-execution)

**OpenAI Agents SDK (JS/TS)**
- Tools with `needsApproval: true` pause the run. The caller iterates `result.interruptions`, calls `state.approve(i)` or reject, then `run(agent, state)`. This works after handoffs and in nested calls. — [OpenAI, Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)
- `maxTurns` caps the loop and throws `MaxTurnsExceededError`. — [@openai/agents README](https://unpkg.com/@openai/agents@0.0.8/README.md) (early 2025 version)
- **Secondary**: `RunState` serialises to a string that can be stored in a DB while waiting for approval. — [Towards AI, HITL as architecture](https://pub.towardsai.net/human-in-the-loop-as-an-architecture-not-a-popup-864f8ac9fd3e)

**Mastra (TypeScript)**
- A workflow step calls `suspend(payload)` with `suspendSchema`/`resumeSchema` (zod). Snapshots go to storage (LibSQL by default) in a `workflow_snapshots` table keyed by run ID, survive restarts and deploys, and are resumed with `run.resume({step, resumeData})`. — [Mastra, suspend and resume](https://mastra.ai/docs/workflows/suspend-and-resume); [Mastra snapshots](https://mastra.ai/docs/workflows/snapshots)
- Agent-level tool approval: `requireToolApproval` per request or `requireApproval` per tool (OR logic), resolved with `approveToolCall({runId})`/`declineToolCall`. `Agent.listSuspendedRuns()` reads paused runs from storage "after a server restart and across multiple server instances". Without a storage provider the result is "snapshot not found". — [Mastra agent approval](https://mastra.ai/docs/agents/agent-approval); [Mastra blog, when to use agent approval](https://mastra.ai/blog/human-in-the-loop-when-to-use-agent-approval)

**CrewAI**
- Per-agent limits: `max_rpm` (requests per minute, default None), `max_iter` (default 20 or 25, depending on the docs page; the docs conflict), `max_execution_time` (seconds, default None), `max_retry_limit` (default 2). — [CrewAI agents docs](https://docs.crewai.com/en/concepts/agents); [CrewAI core concepts](https://docs.crewai.com/core-concepts/Agents/)

### Inferences
- **Approval as persisted interrupt is the industry norm.** LangGraph, MAF (`RequestPort` plus checkpoint), OpenAI (`RunState`), Mastra (snapshot plus `listSuspendedRuns`) and Cloudflare (Workflows) all model "ask the human" as serialised run state plus a pending-request record keyed by ID, resumable on any node after restart. Our Telegram approval for the 5-step release should be modelled the same way: a Postgres row (request ID, step, payload, deadline), resume by ID through LISTEN/NOTIFY, and no actor blocked in memory while waiting. Mastra's `listSuspendedRuns()` is a useful API shape: "show me everything waiting on the owner."
- **Resume re-runs the step** (LangGraph semantics). Every release step that has side effects (tag, publish, post) needs an idempotency key, or it will double-fire after a crash between "did it" and "checkpointed it".
- **Cloudflare's defaults are a useful calibration** for our supervisor and backoff: 3 attempts, 100 ms base, 3 s cap, a 30 s hung-schedule timeout, and one alarm per actor multiplexed over a schedules table. Our per-turn timeouts for LLM calls are necessarily much longer (minutes), so hung-turn detection should be separate from the message-retry policy.
- **Budgets are mostly iteration caps** (CrewAI `max_iter`, OpenAI `maxTurns`), sometimes RPM (CrewAI `max_rpm`), and rarely cost (Akka inline evaluation). An actor runtime that meters tokens per pid and per issue and *refuses the next LLM call* (enforcement, not an alert) would be ahead of most frameworks.
- **Scale-to-zero virtual actors** (Dapr, Cloudflare, Rivet) are the main capability a BEAM-style runtime lacks by default. Idle bees waiting on CI or review should be passivated to Postgres and reactivated by key, not kept as live processes.

### Gaps
- No primary source found for LangGraph's `recursion_limit` default or for the full durability-mode list beyond `"exit"`.
- Tracing specifics (OpenTelemetry spans per agent turn) for Akka, Dapr, Mastra and CrewAI were not verified. The Akka page does not mention tracing.
- No independent benchmarks for Dapr's or Akka's scale claims were found.
- Ray: no primary doc describing "one Ray actor per agent" in a mainstream agent framework was found. Ray's relevance is mainly RL training (OpenRLHF), which was not researched further.

## Q3. Multi-agent coding swarms: scheduling many agents, workspace isolation, failure and retry, throughput measurement

### Takeaway
The coding-agent products converge on: one isolated sandbox (container, VM or worktree) per task, one branch and PR per task, human or CI gates before merge, and planner/worker hierarchies rather than flat peer swarms. Two first-party reports matter most for our design. Cursor (Jan 2026) measured that lock-based task claiming made 20 agents perform like 2-3 and switched to optimistic concurrency plus a planner/worker/judge hierarchy. Cognition (Apr 2026) reports that parallel *writers* still fail and that "single writer, many contributors" (e.g. a reviewer agent) works.

### Cited Findings
**Cursor, "Scaling long-running autonomous coding" (Wilson Lin, 2026-01-14)**
- Flat peers claiming tasks via a shared file plus locks: "Twenty agents would slow down to the effective throughput of two or three, with most time spent waiting." (**measured**, internal). Agents held locks too long or forgot to release them, and a crash while holding a lock stalled others. **Secondary detail.** — [Cursor blog](https://cursor.com/blog/scaling-agents); [ZenML LLMOps summary](https://www.zenml.io/llmops-database/scaling-multi-agent-autonomous-coding-systems)
- Fix: optimistic concurrency, where "writes would fail if the state had changed since they last read it". Then a hierarchy: planners (which can spawn sub-planners) create tasks, workers "just grind on their assigned task until it's done, then push their changes", and a judge decides at the end of each cycle whether to continue, with the next iteration starting fresh. — [Cursor blog](https://cursor.com/blog/scaling-agents)
- Scale: "hundreds of concurrent agents on a single project" and "trillions of tokens" toward one goal. Outputs: a browser with >1M LoC across 1,000 files in about a week, a Solid→React migration over 3 weeks (+266K/-193K), a Java LSP (7.4K commits, 550K LoC), a Windows 7 emulator (14.6K commits, 1.2M LoC), Excel (12K commits, 1.6M LoC). These are self-reported. — [Cursor blog](https://cursor.com/blog/scaling-agents)
- Model per role: GPT-5.2 was better at extended autonomous work and planning, while Opus 4.5 "tends to stop earlier and take shortcuts". Open problems: agents "occasionally run for far too long", periodic fresh starts are still needed against drift and tunnel vision, and planners do not yet wake when their tasks complete. — [Cursor blog](https://cursor.com/blog/scaling-agents)

**Anthropic, C compiler with parallel Claude agents (Nicholas Carlini, Feb 2026)**
- 16 agents (Opus 4.6), close to 2,000 Claude Code sessions, about $20,000 API cost, a 100,000-line Rust C compiler that builds Linux 6.9 on x86, ARM and RISC-V. **Self-reported**, and the cost is an estimate. — [Anthropic engineering](https://anthropic.com/engineering/building-c-compiler); [The Register, 2026-02-09](https://www.theregister.com/2026/02/09/claude_opus_46_compiler/); [Futurum](https://futurumgroup.com/insights/truth-or-dare-what-can-claude-agent-teams-and-developers-create-today/)
- **Secondary**: each instance ran in its own Docker container cloning a shared repo, claimed tasks by writing lock files, pushed upstream and resolved merge conflicts itself. There was no orchestrator; "Claude picks up the 'next most obvious' problem." Failure mode: "Claude can't tell time and, left alone, will happily spend hours running tests instead of making progress." — [fanaticalfuturist summary](https://www.fanaticalfuturist.com/2026/01/16-claude-code-agents-built-a-new-c-compiler-for-20000-from-scratch-in-2-weeks/); [The Register](https://www.theregister.com/2026/02/09/claude_opus_46_compiler/)

**Cognition / Devin**
- "Don't Build Multi-Agents" (mid-2025): parallel subagents make conflicting implicit decisions (the Flappy Bird example). The default is a single-threaded linear agent plus context compression. **Secondary summaries.** — [LangChain, how and when to build multi-agent systems](https://blog.langchain.com/how-and-when-to-build-multi-agent-systems); [jxnl.co](https://jxnl.co/writing/2025/09/11/why-cognition-does-not-use-multi-agent-systems/)
- "Multi-Agents: What's Actually Working" (2026-04-22): "multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions". Devin Review "catches an average of 2 bugs per PR, of which roughly 58% are severe" (**vendor-measured**). A manager Devin spawns child Devins over an internal MCP ("map-reduce-and-manage"). Failure modes: managers are over-prescriptive, and agents wrongly assume they share state with children. Parallel-writer swarms still lack "meaningful adoption", and unstructured swarms are "mostly a distraction". — [Cognition blog](https://cognition.com/blog/multi-agents-working)

**GitHub Copilot coding agent** (GA 2025-09-25)
- Assigning an issue to Copilot gets a 👀 reaction, then a `copilot/` branch, a draft PR linked to the issue, and a session in a GitHub Actions-powered environment. Commits are pushed with status in the PR body, and the agent then requests review. The environment is customisable via an Actions workflow file. The agent's PRs "require human approval before any CI/CD workflows are run", and branch protections apply. Before opening the PR it self-reviews with Copilot code review plus CodeQL, secret scanning and dependency checks. It is positioned for "low-to-medium complexity tasks in well-tested codebases". — [GitHub blog, meet the new coding agent](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/); [GitHub changelog GA](https://github.blog/changelog/2025-09-25-copilot-coding-agent-is-now-generally-available/); [GitHub docs, code review](https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review)

**OpenHands**
- Every action executes in a Docker runtime that isolates the host. A remote runtime enables many runtimes in parallel, and 32-way parallelism cut a SWE-Bench Lite evaluation from days to hours (**measured**, by the vendor). "Scale from one to thousands of agents" is a **vendor claim**. Large refactors are a target use case, described as "highly automatable but hard to one-shot". — [OpenHands, SWE-bench at 30x speed](https://openhands.dev/blog/evaluation-of-llms-as-coding-agents-on-swe-bench-at-30x-speed); [openhands.dev](https://openhands.dev); [AI Engineer talk](https://ai.engineer/talks/automating-large-scale-refactors-with-parallel-agents)

**Claude Code subagents and agent teams** (agent teams experimental, shipped Feb 2026)
- A team is a lead plus teammates (separate Claude Code instances), a shared task list and a mailbox. Each mailbox is a JSON file at `~/.claude/teams/{team}/inboxes/{agent}.json`, and a message counts as sent only if the write succeeds. Tasks are pending, in progress or completed, with dependencies, and "Task claiming uses file locking to prevent race conditions". Completing a task auto-unblocks its dependents. — [Claude Code docs, agent teams](https://code.claude.com/docs/en/agent-teams)
- Hooks act as quality gates: `TeammateIdle`, `TaskCreated` and `TaskCompleted`, where exit code 2 rejects the transition and sends feedback. A teammate whose turn ends on an API error notifies the lead with the error text. A message wakes a teammate waiting on API retry backoff so it retries immediately. — [same](https://code.claude.com/docs/en/agent-teams)
- Guidance: start with 3-5 teammates, aim for 5-6 tasks per teammate, and "token costs scale linearly". Limitations: no resume of in-process teammates, "task status can lag ... which blocks dependent tasks", slow shutdown, no nested teams, and a lead that can declare done early. Inter-agent messages are marked as coming from another agent, so a teammate "can't approve a permission prompt or supply consent on your behalf". — [same](https://code.claude.com/docs/en/agent-teams)
- Worktrees are the recommended isolation for parallel sessions. "Two teammates editing the same file leads to overwrites." — [same](https://code.claude.com/docs/en/agent-teams)

### Inferences
- **Task claiming should not be a long-held lock.** Cursor's measurement (20 agents → 2-3 effective) and Claude Code's "task status can lag" both point to the same remedy for the Queen: claim issues with a compare-and-set (`UPDATE ... WHERE state='open' AND version=$v`) or a short **lease with expiry and heartbeat**, so a crashed bee's claim lapses automatically. Never use an advisory lock held for the whole bee run. Postgres LISTEN/NOTIFY is a good fit for "task unblocked" wake-ups. This is exactly the "planners don't wake when tasks complete" gap Cursor names.
- **Single writer per artifact.** Cognition's "writes single-threaded" and Claude Code's "each teammate owns a different set of files" support one bee per issue/branch, with the reviewer as a separate read-only actor. A reviewer that sees only the diff in a clean context is the pattern Cognition measured (2 bugs/PR).
- **Periodic fresh starts are a supervisor feature.** Cursor's drift and tunnel vision and Carlini's "can't tell time" mean a bee needs a wall-clock budget and a turn budget, with restart-from-plan when exceeded. That is a supervision strategy (restart with clean context), not only a timeout.
- **Throughput metrics used in public:** commits/hour, LoC, PRs, bugs per PR, % severe, cost per project, and wall-clock for a parallel eval. None of the sources report a standard "merged PRs per agent-hour" or "cost per merged PR". That metric would be our own, and worth publishing.
- **The human gate is on CI, not only on merge.** Copilot does not run CI on agent PRs without human approval, which is a cost and security control. The Queen's equivalent is that CI and Actions minutes are a shared budget the runtime should meter.

### Gaps
- No public numbers on Copilot coding agent concurrency limits per repo, retry policy, or session timeouts.
- No primary text for the original "Don't Build Multi-Agents" post (summaries only). Carlini's lock-file mechanics come from secondary coverage.
- SWE-agent orchestration at scale (e.g. SWE-smith/SWE-ReX parallel runs) was not researched.
- Devin's per-session isolation (VM per session) and its scheduling of parallel sessions were not documented in the sources found.

## Q4. TypeScript/JS actor libraries (XState v5, Effect, RivetKit, nact, Comlink/workers): what they give over a hand-rolled runtime

### Takeaway
No JS library offers the full BEAM package (pids, links and monitors, supervisors, distribution). Each covers one slice better than a typical hand-rolled runtime. Effect gives structured concurrency (child fibers interrupted with their parent, finalizers run on interrupt), typed errors, `ExecutionPlan` retry and fallback across LLM providers, a token-bucket `RateLimiter`, and `@effect/cluster` (single-threaded entities, SQL-backed mailboxes, durable workflows with compensation). XState v5 gives typed, inspectable actor hierarchies where invoked actors are bound to state lifetime. RivetKit gives Cloudflare-DO-style keyed, durable, hibernating actors that also run on Node/Bun. nact is Akka-style but low-activity.

### Cited Findings
**Effect (Effect-TS)**
- Structured concurrency: `Effect.fork` ties the child's lifetime to the parent, and children end when the parent is terminated, including nested children. Interruption "immediately stops the fiber and safely runs all finalizers to release any resources". `Fiber.interrupt` waits for full termination by default. `forkDaemon` (global scope) and `forkScoped`/`forkIn` give explicit escape hatches. — [Effect docs, fibers](https://effect.website/docs/concurrency/fibers/)
- `@effect/cluster`: durable workflows were added in June 2025, along with shard groups (entities targeting specific runners), `ClusterCron`, a fix so "Workflow.interrupt triggers compensation", and a fix to avoid resuming already-running workflows. — [This Week in Effect, 2025-06-06](https://effect.website/blog/this-week-in-effect/2025/06/06/)
- v4 docs: workflow executions, activities, resumes, interrupts and durable clock wake-ups are coordinated through persisted cluster entities. The engine needs `Sharding` plus `MessageStorage`. `SingleRunner` runs everything in one process but still needs SQL because "mailbox messages and replies are stored in SQL". Entity handlers process messages one at a time. The modules are marked **unstable** (`effect/unstable/cluster`, `effect/unstable/workflow`). — [Effect v4 API, ClusterWorkflowEngine](https://effect.website/docs/v4/api/effect/unstable/cluster/ClusterWorkflowEngine); [Effect v4 API, SingleRunner](https://effect.website/docs/v4/api/effect/unstable/cluster/SingleRunner)
- LLM-specific: `ExecutionPlan` (since v3.16.0) provides different resources per step (e.g. a different `LanguageModel` layer) with `attempts` and `schedule`, so retry-then-fallback to another provider is declarative. `@effect/ai` is provider-agnostic, with OpenAI, Anthropic, OpenRouter and OpenAI-compatible packages. The core `RateLimiter` is a token bucket that counts only effect *starts* ("concurrent executions are not capped"). The v4 persistence `RateLimiter` supports keyed limits with in-memory or Redis stores. — [Effect API, ExecutionPlan](https://effect.website/docs/v3/api/effect/ExecutionPlan); [Effect API, RateLimiter](https://effect.website/docs/v3/api/effect/RateLimiter); [Effect v4 persistence RateLimiter](https://effect.website/docs/v4/api/effect/unstable/persistence/RateLimiter); [Effect AI intro](https://effect.website/docs/ai/introduction/)

**XState v5 (Stately)**
- Invoked actors start when a state is entered and stop when it is exited. Many actors can be invoked per state, and any actor (promise, callback, machine) can be invoked. `spawn`/`spawnChild` create dynamic actors with `id`, `input` and a system-wide `systemId`. — [Stately docs, invoke](https://stately.ai/docs/invoke); [Stately docs, spawn](https://prod.stately.ai/docs/spawn)
- The actor system is created implicitly from the root actor (`createActor(machine).start()`), and peers are found via `system.get(systemId)`. v5 renames: `interpret()`→`createActor()`, `withConfig()`→`provide()`, `services`→`actors`. — [Stately docs, system](https://prod.stately.ai/docs/system); [Stately migration v4→v5](https://stately.ai/docs/migration.mdx)

**RivetKit (@rivetkit / Rivet Actors)**
- A TypeScript port of the Rivet Actors service (July 2025): "long-running, lightweight processes designed for stateful workloads". State is in memory with automatic persistence, and the docs say to "create one per agent, per session, or per user". Clients get-or-create an actor by key, call actions and subscribe to events. In dev, actors run in-process with no servers. — [Rivet changelog 2025-07-01](https://rivet.dev/changelog/2025-07-01-introducing-rivetkit-backend-libraries-that-replace-saas/); [Rivet Node/Bun quickstart](https://rivet.dev/docs/actors/quickstart/backend/)
- Drivers: file system (dev default), memory, Rivet engine (cloud or self-host), Cloudflare Durable Objects. Each instance is a "runner", and multiple runners scale horizontally. A ~20 ms cold start is a **vendor claim**. — [Rivet architecture docs](https://rivet.dev/docs/general/architecture/)

**nact**
- Akka/Erlang-inspired Node actors with supervision policies and persistent (event-sourced) actors via `@nact/persistence`. Latest npm 7.6.2 with one maintainer and about 564 weekly downloads. A rearchitecture (TypeScript port, location transparency) sits on a `next` branch. The README still says Node 8+. — [nact on npm](https://npmjs.org/package/nact); [nact GitHub](https://www.github.com/nactio/nact)

### Inferences
- **What to borrow rather than adopt:**
  1. Effect-style structured interruption. When a supervisor kills a bee, every child (LLM stream, `git` subprocess, test run) is interrupted and finalizers run, e.g. worktree cleanup. The memory notes on leaked worktrees filling runner disks (bee-runner-disk-jam) are exactly the bug class finalizers-on-interrupt prevent.
  2. Effect `ExecutionPlan`-style declarative retry→fallback per LLM call.
  3. Keyed rate limiters per provider and per credential, distinct from concurrency caps. Effect's own doc warns that a start-counting limiter does not cap concurrency, so you need both.
  4. XState-style "child lifetime bound to parent state". The release workflow's step actors are invoked per state and die on transition.
  5. Rivet/Cloudflare-style get-or-create-by-key plus passivation.
- `@effect/cluster` is architecturally the nearest neighbour to the Queen runtime (single-threaded entities, SQL-persisted mailboxes, sharding over runners, durable workflows with compensation, cron). Its v4 modules are still "unstable", so it is a design reference more than a dependency.
- Typed messages: XState and Effect (Schema/RPC-defined entities) give compile-time message protocols. A hand-rolled runtime with `unknown` payloads loses this. Adding a schema per mailbox (zod/Effect Schema) is cheap and catches the "message format drifted between deploys" class of error. Claude Code's mailbox validates each entry and drops malformed ones, after an earlier version blocked a mailbox on one malformed entry.

### Gaps
- Comlink / worker-thread RPC and "ts-actors" were not researched. No sources were gathered on their 2025-2026 status.
- Effect has no built-in Erlang-style supervisor *tree* with restart intensity limits documented in the sources found. Whether `@effect/cluster` provides restart-intensity semantics is unverified.
- No benchmarks comparing RivetKit, Effect cluster and a hand-rolled Bun runtime were found.

## Q5. Evidence on failure modes of agent swarms (runaway loops, cost blowups, stuck agents, duplicated work) and how platforms prevent them

### Takeaway
The best quantitative evidence is the MAST study (NeurIPS 2025): 41%-86.7% failure rates across 7 open-source multi-agent systems, dominated by system-design failures (step repetition 15.7%, unaware of termination 12.4%) and weak verification. Interventions gave at most +15.6%. First-party engineering reports (Anthropic, Cursor, Carlini) confirm the same modes in production: over-spawning, duplicated work, endless searching, lock contention, drift, and agents that run too long. Cost multiplies with agents (about 4x chat for one agent, about 15x for multi-agent). Widely circulated "runaway loop" dollar figures ($47k) are unverified.

### Cited Findings
**MAST, "Why Do Multi-Agent LLM Systems Fail?"** (arXiv 2503.13657, v3 Oct 2025, NeurIPS 2025)
- 7 frameworks studied: MetaGPT, ChatDev, HyperAgent, AppWorld, AG2, Magentic-One, OpenManus. There are 1,642 annotated traces, with Cohen's kappa 0.88 for annotators, plus an LLM-as-judge annotator. Failure rates range from "41% to 86.7%". — [arXiv HTML v3](https://arxiv.org/html/2503.13657v3); [NeurIPS 2025 poster](https://neurips.cc/virtual/2025/poster/121528)
- 14 modes (**measured** prevalence):
  - System design: disobey task spec 11.8%, disobey role spec 1.5%, **step repetition 15.7%**, loss of conversation history 2.8%, **unaware of termination conditions 12.4%**.
  - Inter-agent misalignment: conversation reset 2.2%, fail to ask for clarification 6.8%, task derailment 7.4%, information withholding 0.85%, ignored other agent's input 1.9%, reasoning-action mismatch 13.2%.
  - Task verification: premature termination 6.2%, no or incomplete verification 8.2%, incorrect verification 9.1%.
  — [arXiv HTML v3](https://arxiv.org/html/2503.13657v3) (category totals of roughly 44% / 32% / 24% are my sums, not the paper's)
- Interventions: in ChatDev, giving the CEO the final say gave +9.4% task success, and adding a high-level objective-verification step gave +15.6% on ProgramDev, the stated maximum improvement. MetaGPT had 60-68% fewer FC1/FC2 failures than ChatDev but 1.56x more verification failures. — [arXiv HTML v3](https://arxiv.org/html/2503.13657v3)

**Anthropic multi-agent Research system** (June 2025)
- "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats". "Token usage by itself explains 80% of the variance" on BrowseComp. Lead Opus 4 with Sonnet 4 subagents beat solo Opus 4 by 90.2% on an internal eval (**vendor-measured**). — [Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- Early failures: "spawning 50 subagents for simple queries", "scouring the web endlessly for nonexistent sources", "distracting each other with excessive updates", and duplicated work ("2 others duplicated work ...") under vague delegation. The fix was explicit effort-scaling rules in the prompt: 1 agent with 3-10 tool calls for simple tasks, 2-4 subagents with 10-15 calls for comparisons, and 10+ subagents only for complex work. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Reliability: "systems that can resume from where the agent was when the errors occurred", "retry logic and regular checkpoints", and rainbow deployments so in-flight long-running agents are not broken by deploys. Synchronous subagent execution means "the entire system can be blocked while waiting for a single subagent". Full production tracing was used, and decision patterns were monitored without reading conversation content. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)

**Coding-swarm specifics** (see Q3)
- Lock contention: 20 agents performed like 2-3. Agents run "far too long", and periodic fresh starts are needed. — [Cursor](https://cursor.com/blog/scaling-agents)
- Time-blindness: hours spent re-running tests without progress. About $20k for about 2,000 sessions. — [The Register](https://www.theregister.com/2026/02/09/claude_opus_46_compiler/)
- Stuck dependency chains from stale task status, and leads declaring done early. — [Claude Code docs](https://code.claude.com/docs/en/agent-teams)
- Managers over-prescribe, and children wrongly assume shared state. — [Cognition 2026-04-22](https://cognition.com/blog/multi-agents-working)

**Cost blowups (weak evidence)**
- A "$47,000 agent loop": an Analyzer↔Verifier ping-pong in a 4-agent LangChain pipeline ran 264 hours with no per-agent budget cap. **Unverified**: no original post-mortem was found, and it is repeated mainly by vendors selling budget enforcement. — [dev.to / Waxell](https://dev.to/waxell/the-47000-agent-loop-why-token-budget-alerts-arent-budget-enforcement-389i); [Decryption Digest](https://www.decryptiondigest.com/blog/pre-execution-budget-enforcement-circuit-breaker-ai-agents)
- Single-author reports: $400 in 12 minutes in a CAPTCHA retry loop. Claude Code "puttering" after task completion, consuming tokens with no output (a user issue report). — [futureagi blog](https://futureagi.com/blog/loop-engineering/ai-agent-loop-cost-control/); [claudeissues.com #52362](https://claudeissues.com/issue/52362-agent-enters-infinite-puttering-loop-after-task-completion-consuming-tokens-with)
- Mitigations proposed in those sources: hard enforcement that refuses the next LLM call (as opposed to alerts), loop detection that halts after the same failing tool call with the same args 3 times in a row, and cumulative cost curves with alerts. Iteration caps (CrewAI `max_iter` 20) are necessary but not sufficient. — [Waxell blog](https://waxell.ai/blog/ai-agent-token-budget-enforcement); [futureagi](https://futureagi.com/blog/loop-engineering/ai-agent-loop-cost-control/)

**Platform-level preventions observed**
- Turn and iteration caps: OpenAI `maxTurns` throws `MaxTurnsExceededError` ([README](https://unpkg.com/@openai/agents@0.0.8/README.md)). CrewAI has `max_iter`, `max_execution_time`, `max_rpm` and `max_retry_limit` ([CrewAI docs](https://docs.crewai.com/en/concepts/agents)).
- Cost and quality thresholds interrupt workflows via Akka inline evaluation ([Akka](https://akka.io/blog/introducing-akkas-new-agent-component)).
- Transition gates via hooks that refuse "task complete" or "go idle" (Claude Code `TaskCompleted`/`TeammateIdle`, exit 2) ([Claude Code docs](https://code.claude.com/docs/en/agent-teams)).
- Human approval before CI runs on agent PRs (Copilot) ([GitHub blog](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/)).
- Bounded retries with backoff: Cloudflare 3x, 100 ms→3 s ([Cloudflare](https://developers.cloudflare.com/agents/concepts/agent-class/)).
- Durable resume avoids re-paying tokens after a crash (Dapr Agents) ([CNCF](https://www.cncf.io/announcements/2026/03/23/general-availability-of-dapr-agents-delivers-production-reliability-for-enterprise-ai/)).

### Inferences
- The two most common MAST modes, **step repetition (15.7%)** and **unaware of termination (12.4%)**, are exactly what a runtime (not a prompt) can detect. Candidate detectors: hashing consecutive tool calls and arguments per pid (repeat ≥3 → escalate), and explicit termination conditions per actor type (e.g. a bee terminates on PR opened, explicit give-up, or budget exhausted). Verification failures (~24% combined) argue for a separate reviewer actor with clean context, which is the Cognition and Copilot pattern.
- **Budget must be enforced at the mailbox or LLM-call boundary, per pid and per issue, as a hard stop**, with escalation to the owner via the existing Telegram approval path ("bee #N hit $X; continue?"). Few frameworks do this natively, so it is a genuine differentiator.
- **Duplicated work** in the sources comes from vague delegation (Anthropic) and racy claiming (Cursor). Keyed actors (one per issue) plus CAS or lease claiming addresses the second. Explicit task boundaries in the issue format address the first.
- **Deploys must not kill in-flight long-running agents** (Anthropic's rainbow deploys). This matches the existing Queen practice of draining before deploy (memory: queen-deploy-does-not-stop-swarm). It is worth stating as a runtime guarantee: actors are passivated to Postgres and resumed on the new version.
- **Measure throughput the way the credible reports do**: effective vs nominal parallelism (Cursor's "20 → 2-3" is the metric that exposed the lock problem), cost per finished unit, and bugs caught per PR by the reviewer. Track "agent-time spent waiting on locks, CI, or the owner" as a first-class metric.

### Gaps
- No verified primary post-mortem for any large dollar-figure runaway-loop incident was found.
- No published data on how often coding agents get "stuck" (e.g. % of sessions hitting turn limits) from GitHub, Cognition or OpenHands.
- No measurements of duplicated-work rates in production coding swarms beyond anecdotes. Anthropic's example is qualitative.
- MAST's per-framework failure breakdown (Figure 5) and the AG2 intervention results (Table 5) were not extracted.
