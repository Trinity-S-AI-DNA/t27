MINIMAL REPRO: t27b mis-evaluates bitwise AND/OR/XOR between two large u64
compile-time constants (constant-evaluation defect). Small-operand bitwise ops
and per-literal identity checks pass.

--- begin sha256_micro4.t27 (all asserts; results from `t27b test`) ---
test x_identity { const x : u64 = 2670261550; assert(x == 2670261550); }
  -> PASS
test y_identity { const y : u64 = 172365677; assert(y == 172365677); }
  -> PASS
test and_large { const x : u64 = 2670261550; const y : u64 = 172365677;
    assert((x & y) == 168303660); }                     -> FAIL
test or_large  { ... assert((x | y) == 2674875775); }    -> FAIL
test xor_large { ... assert((x ^ y) == 2506572115); }    -> FAIL
test and_with_one { const x : u64 = 2670261550;
    assert((x & 1) == 0); }                             -> PASS
test or_with_one  { ... assert((x | 1) == 2670261551); } -> PASS
--- end ---

python ground truth for these exact literals:
  x & y = 168303660
  x | y = 2674875775
  x ^ y = 2506572115

commands: `t27b test sha256_micro4.t27` (zig 0.16.0, macOS arm64, 2026-11-01)
relationship to the SHA-256 divergence: the sha256 spec failure is a SEPARATE
cause - its runtime values flow through arrays (K table, message bytes), not
through const-folded bitwise expressions, and the digest remained wrong there
after this defect was excluded.
