# t27b against other compiler pipelines (October 2026)

Data for the t27b v0.2.0 release and the blog post. gHashTag/t27#8817. Raw numbers: [`t27b-bench-2026-10.json`](t27b-bench-2026-10.json).

Everything ran on the Railway t27c lab, at master `9a0f4c394` (2026-10-10). Nothing was built or timed on the owner's Mac. The measurement scripts stay in the lab's scratch directory, because only data and prose may be committed (#8236); every command they ran is spelled out below so the numbers can be reproduced.

**Verdict.** This is not a breakthrough in generated code: t27b's output is at gcc -O0 level, 3 to 5 times behind every optimising pipeline in instructions and in emulated time, and up to 2 times larger. It is not a breakthrough in coverage either; it trails the reference it mirrors by 15 files. Where it is genuinely strong is compile latency and footprint together: a 3 MB, LLVM-free, 5 MiB-of-memory compiler that turns a spec into AArch64 code in about 5 ms, nearly ten times faster than gcc -O0 on the same C, and agrees with the reference on every one of 8,344 tests. That is the profile of a fast baseline compiler, and it is the axis to lead with. The trust story is visible rather than independent, and on Linux t27b is a JIT test runner, not yet a compiler that ships binaries.

## The pipelines

| Name | Front end | Back end | What runs the tests |
|---|---|---|---|
| t27b | t27b's own (it mounts t27c's `bootstrap/src/compiler.rs` front end) | t27b AArch64 code generator, no LLVM | t27b's in-process JIT, under qemu-aarch64. `--overflow trap` is the default; `wrap` drops the overflow checks |
| zig Debug / ReleaseSafe / ReleaseFast | `t27c gen` | zig 0.16 + LLVM | a static aarch64 test binary, under qemu-aarch64 |
| gcc -O0 / -O2 | `t27c gen-c` | aarch64-linux-gnu-gcc 12 | a static aarch64 binary with a generated driver, under qemu-aarch64 |
| clang -O0 / -O2 | `t27c gen-c` | clang 21.1.0 (`zig cc`) | the same driver, musl, under qemu-aarch64 |
| rustc -O0 / -O3 | `t27c gen-rust` | rustc 1.99 | nothing: gen-rust lowers function bodies but no tests (its header says "NOT LOWERED BY THIS BACKEND: N test(s)") |

Safety checks differ, and that matters for every speed number. t27b (trap) and zig Debug/ReleaseSafe check integer overflow and bounds at run time. zig ReleaseFast, gcc and clang do not; in C, signed overflow is undefined behaviour. The fair comparison for t27b's default output is zig ReleaseSafe; ReleaseFast and -O2 are shown as the ceiling.

**t27b on aarch64-linux is a JIT test runner, not an ahead-of-time compiler.** `t27b build` writes a Mach-O object only (`cli/t27b/src/macho.rs`; ELF64 is listed as future work in `cli/t27b/README.md`), it does not link, and it refuses module-level variables in an object file ("no writable data section"; 2 of the 20 axis-C specs). So t27b cannot produce a runnable aarch64-linux executable today. All t27b run times below are JIT runs.

## A. Coverage and correctness

**Denominator.** Every `.t27` file under `specs/`: 1,819 files (`find specs -name '*.t27'`), the same set `t27b corpus specs` walks. Nothing is left out for being slow or broken.

**What each pipeline did per file.**

- t27b: `qemu-aarch64 t27b corpus specs --json --jobs 6 --timeout-ms 60000 --reference t27c`, which runs every file through `t27b test --check` (JIT plus interpreter) and, with `--reference`, `t27c test-report` (t27c gen + zig Debug, natively on x86_64) on the same file, and compares the two test by test.
- zig, gcc, clang: generate, compile for aarch64-linux, then list the tests and run **each test in its own qemu-aarch64 process**, with a 120 s limit per test and 600 s per compile. That is the same one-test-per-process protocol as `t27c test-report` (its runner source is copied verbatim). For C, the driver calls the `test_*` functions gen-c emits.
- rustc: generate and compile only.

**Classes.** Every file is counted once, in one class, so each row sums to 1,819:

- *pass*: it compiled, it has at least one test, and every test passed;
- *pass, vacuous*: t27b only; every test passed but no runtime assert executed (#6115);
- *compiled, no tests*: nothing to run (t27b's and the reference's own tallies count these as passes; here they are kept apart);
- *a test fails*: at least one test failed or crashed;
- *timeout*: every non-passing test hit the time limit;
- *blocked*: it did not generate, did not compile, or t27b refused a construct.

## B. Compile speed

### Method

- **t27b is measured natively.** The lab is x86_64, so t27b was also built for the host. On x86_64 `t27b build -o x.o` works (it cross-compiles to an AArch64 Mach-O object), and `t27b test` runs the front end and code generation, tests included, and then stops with exit 74 when it tries to map the JIT. The wall time of that process is t27b's compile time with tests ("test-compile"); `t27b build` is its time to an object without tests.
- **Emulation, calibrated.** The aarch64 t27b under qemu reports its own phase times (`--time`). Its compile phases took a geomean **20x** longer than the native test-compile process on the same specs (7x on the largest, `t27core` and `gf16`; 36x to 56x on the small kernels, where qemu's translation warm-up dominates). So t27b compile times measured under qemu, including the earlier report's 33 to 86 ms, overstate native time by an order of magnitude.
- **Everything else is native x86_64 too:** `t27c gen*`, zig, gcc, clang, rustc.
- **What one sample is:** the wall time of one process, from spawn to exit, measured by the harness. One compile at a time, nothing else of ours running. Order: round-robin over specs and pipelines, 6 rounds. Round 0 is reported as *cold* (the first time that compiler sees that file in this pass); rounds 1 to 5 are *warm*, and their median and minimum are reported. The host load was recorded with every sample.
- **Cold is not a cold disk cache.** The container cannot drop the kernel page cache, so cold means first run of the pass. For zig, warm means a warm *global* cache (compiler_rt and libc already built) with an empty local cache. Reusing the local cache did not help: with `-femit-bin` to a path, a second compile into the same cache took the same time (3.07 against 3.08 s in Debug, 14.17 against 14.12 s in ReleaseFast), so zig rebuilt. The truly cold first build, with an empty global cache, is measured separately below.
- **Set:** the 20 tier-1 specs from axis C, plus 567 specs for the cheap pipelines (B2).

## C. Generated code

### Which specs

**Tier 1, chosen by a rule that never looks at t27b.** Start from the 567 files that *every* pipeline passes (t27b, zig Debug and ReleaseFast, gcc and clang at -O0 and -O2). Build each with gcc -O0 and count the guest instructions its tests execute. Take the 20 with the most. The full ranked list of all 567, with gcc -O0/-O2, clang -O0/-O2 and t27b counts, is in the JSON (`axis_C.selection`). The rule picks the six `benchmarks/kernel_*` specs, three openxc7-synth simulations, the t27a ISA, and ten others.

**Tier 2, named in the brief, t27b and zig only.** The brief named sha256, ed25519, gf16, sorting, matrix and bigint. gen-c output for sha256, sha512, ed25519 and gf16 does not compile with gcc or clang, so they cannot be in tier 1; they are measured against zig only. The sorting, matrix and bigint specs (`tri/sort/*`, `tri/math/matrix`, `numeric/bigint`, `ternary/bigint`) do not compile in *any* pipeline, the reference included, so they are not measured.

### How

- **Run time:** every test once, in order, in one process, each call bracketed by `CLOCK_MONOTONIC` reads inside the guest. For t27b that is `t27b test --time` (its `TIME <test> <ns>` lines, around `jit.call`). For zig it is a short custom test runner that does the same; for C, the generated driver does the same. The per-spec number is the sum over the tests every pipeline ran (t27b also runs invariants at run time, which zig folds at compile time and gen-c drops; those are left out of the sum). 5 repetitions, round-robin over specs and pipelines, median and min.
- **Everything runs under the same qemu-aarch64 7.2, so these are emulated times.** They rank pipelines relative to each other on this host; they are not arm64 speed. Emulation cost is not uniform across instruction kinds: on `kernel_sieve`, zig ReleaseFast executes 43% fewer instructions than t27b and still takes 25% longer under qemu.
- **Instructions executed:** a 39-line qemu TCG plugin (lab scratch, built against `qemu-plugin.h` from qemu v7.2.0, sha256 `19f277b0...`) adds each translated block's instruction count at block entry. For zig and C it counts only between two `getppid()` markers the runners place around each test call (inside the clock reads). For t27b it counts only blocks inside memory the process made executable with `mprotect(PROT_EXEC)`, which is the JIT image. This number is deterministic. It includes t27b's run-time invariants (under 6% of t27b's test time on every spec, under 0.1% on most), and for t27b it leaves out the host code that `jit.call` runs.
- **Code size:** bytes of machine code for the spec's functions and tests. t27b: the JIT image (`t27b code: N bytes in the JIT image`, which includes its entry trampoline and `__t27b_*` helpers). zig: the summed `nm` sizes of code symbols in the generated module's namespace, from a build with `std.testing.refAllDecls` added so that functions no test calls are compiled too. gcc and clang: all `.text*` sections of `gen-c`'s object. rustc and `t27b build` objects have no tests and are compared with each other.
- `(f)` marks a pipeline that executed less than 1% of gcc -O0's instructions on that spec: it evaluated the test at compile time. clang -O2 does that on 11 of the 20 tier-1 specs; those are left out of its averages.

What the numbers say:

- **t27b's code is at the level of an unoptimising compiler.** It executes about as many instructions as gcc -O0 (0.91x) and runs about as fast under qemu (1.11x). It beats unoptimised LLVM output: half of zig Debug's instructions (0.54x) and 0.41x of clang -O0's.
- **Every optimising pipeline is 3 to 5 times better.** Against the like-for-like checked build, zig ReleaseSafe, t27b executes 3.2x the instructions and takes 3.4x the time. Against gcc -O2: 3.4x and 4.1x. Against zig ReleaseFast: 4.5x and 4.1x. Against clang -O2 where it did not fold the test away: 3.5x and 3.7x.
- **Its code is larger than every optimising build** (1.8x gcc -O2, 1.9x zig ReleaseSafe, 2.0x zig ReleaseFast) and 1.34x gcc -O0. It is smaller than zig Debug (0.66x) and clang -O0 (0.65x). Without tests, `t27b build`'s objects are 0.73x rustc -O0's and 2.0x rustc -O3's (13 to 17 specs where gen-rust compiles).
- **Overflow checks cost about 12% of the instructions** (trap/wrap 1.12x) and 24% of the emulated time.
- **One pathological case:** `compiler/core/t27core` takes 544 ms under t27b against 66 ms under zig Debug, although t27b executes fewer instructions (4.9 M against 7.5 M). Before every test, `jit.call` copies the whole module-variable image so each test starts from fresh state; t27core has large module-level arrays, so each of its 95 tests pays at least 2.8 ms for the copy. zig and C keep module state across tests and pay nothing.
- **Disagreement with the earlier report.** `docs/reports/2026-10-09-sieve-c6-c7.md` found the t27b run phase faster than zig ReleaseFast on `kernel_collatz` (1,207 against 1,533 ms). Here zig ReleaseFast takes 361 ms against t27b's 1,474 ms and executes 0.54x t27b's instructions. That run used another host (AMD EPYC 9655) and timed the default runner's process; it is not re-run here, and the instruction counts above do not support the earlier observation.

- **Every pipeline is deterministic in place:** all outputs are bit-identical between the two builds in the same directory.
- **t27b, t27c's generators, gcc and rustc are also path-independent:** identical from another directory.
- **zig and `zig cc` (clang) are not path-independent by default.** Their outputs carry DWARF debug information that records the build directory. After `objcopy --strip-debug`, the zig Debug and ReleaseFast test binaries and the clang -O2 object were identical across directories (checked on the first spec). gcc was run without `-g`, so it had no paths to record; this is not a claim that gcc output is path-independent with debug info.
- t27b has 18 builds, not 20: `t27b build` and `t27b asm` refuse the two specs with module-level variables.

The t27b lab's signed receipts depend on this property: a receipt is a Merkle root over per-file verdicts and asm outputs, so two runs of the same commit must produce the same root.

## Where t27b loses

These are as much the result as the wins, and the release notes should carry them.

1. **Generated code is at -O0 level.** Over the 20 tier-1 specs, t27b executes 3.4x the instructions of gcc -O2, 3.2x zig ReleaseSafe (the build with the same run-time checks), 4.5x zig ReleaseFast, and 3.5x clang -O2 where clang did not fold the test away. Under qemu that is 3.4x to 4.1x the run time. It is level with gcc -O0 (0.91x instructions, 1.11x time). It beats only unoptimised LLVM output (zig Debug, clang -O0). On crypto (tier 2) the gap to zig ReleaseFast is 10x in instructions.
2. **Its code is bigger** than every optimising build: 1.8x gcc -O2, 1.9x zig ReleaseSafe, 2.0x zig ReleaseFast, 1.34x gcc -O0.
3. **Coverage trails the pipeline it mirrors.** 15 files the reference passes do not pass in t27b (14 blocked, 1 vacuous); zig on aarch64 passes all 1,311. The blockers are i128, frame addresses that escape, empty typed array literals, `@cos`, `anytype`, `std.*`, and a 1 MiB frame limit.
4. **No ahead-of-time executable on Linux.** `t27b build` writes Mach-O only (no ELF), does not link, and refuses module-level variables in an object file. On aarch64-linux, t27b runs tests in its JIT; it cannot ship a binary. Every other pipeline here produces a static aarch64-linux executable.
5. **Per-test state reset costs time.** `jit.call` copies all module variables before every test. A spec with large module arrays pays it on every test: `compiler/core/t27core` runs 8.3x slower than zig Debug although t27b executes fewer instructions.
6. **The self-generated share is 12%, not 36%, of the code t27b runs.** 36% is the share of t27b's own backend (`gen/rust/tri/t27b` against `cli/t27b/src`). t27b also mounts t27c's hand-written front end (48,277 lines). Its tests are hand-written Rust (8,349 lines). It is compiled by rustc, so it is not self-hosted.
7. **Its verification is mostly self-consistency.** DDC ends in `DDC_BACKEND_AGREEMENT` (one shared front end), the JIT/interpreter check shares one IR, and the reference shares the front end. The random-program fuzzer, the check that reaches beyond the corpus, currently finds 7 disagreements per 1,000 programs.
8. **Zig amortises; t27b does not.** Compiling all 20 specs in one invocation cuts zig's per-spec cost to 0.31 s (Debug) and 1.65 s (ReleaseFast); t27b's compile-speed lead then falls from about 640x to about 9x (Debug) and from about 2,900x to about 46x (ReleaseFast).


## Caveats

- **Emulated run time.** All run times are qemu-aarch64 on x86_64. They rank pipelines on this host only, and emulation cost varies by instruction mix (see `kernel_sieve`). The instruction counts do not depend on the host and are the better measure of code quality here. No native arm64 per-spec timings exist: the `t27b-native-ratchet` CI job logs only a whole-corpus time (446 s at this commit, with a cached reference), so native timings were not added.
- **A shared machine.** Other agents' jobs ran on the same host throughout. The host load average ranged from 27 to 103 on 48 threads; during the timing passes this container ran one compile or one test binary at a time (about 4% of its 24-CPU quota). Every sample carries its load in the JSON. The spread is not small, which is why medians are reported: over 5 runs, max/min - 1 was 9% at the median and 20% at the 90th percentile for run times of 100 ms or more (30% worst); for warm compiles it was 10% (zig Debug) and 7% (zig ReleaseFast) at the median, but 34% for t27b and 36% for gcc -O0, whose samples are a few milliseconds long and are dominated by scheduling noise (one t27b sample of 8 ms against a 1 ms minimum).
- **Process wall time.** Compile times include process start (about 1 ms for t27b and t27c). The calibration factor compares qemu phase times (no process start) with native process wall time, so it slightly understates the emulation overhead on the smallest specs.
- **Cold** means the first run of a pass, not an empty page cache, which the container cannot drop. zig's truly cold first build is measured separately.
- **Different run-time contracts.** t27b re-initialises module variables before each test; the zig and C runners do not. t27b also runs invariants at run time; zig evaluates them at compile time and gen-c drops them (left out of the run-time sums; included in t27b's instruction counts, under 6%).
- **Instruction-count details.** Counts are per translated block, so a block that traps mid-way is counted whole. The zig and C windows include the `getppid()` marker's libc wrapper (about 20 instructions with glibc, more with musl), which matters only for tiny tests. t27b's count leaves out host code in `jit.call`.
- **Undefined behaviour in gen-c output** changes C verdicts with the optimisation level (axis A), and an optimiser may exploit it for speed. C numbers are reported as measured.
- **Selection.** Tier 1 is the top 20 by gcc -O0 instructions among the 567 files every pipeline passes. That population excludes everything gen-c cannot compile, including the crypto specs; tier 2 measures those against zig. clang -O2 folds 11 of the 20 tier-1 tests at compile time; those are left out of its averages (with them, the "ratio" would be meaningless: up to 7,600,000x).
- **clang** is zig 0.16's bundled clang 21.1.0 with musl, not a distribution clang with glibc. No standalone clang was installed.
- **gen-rust** lowers no tests, so it appears only in A (compiles), B, C (size without tests) and E.
- **Instrument bugs found during the run, and fixed before these numbers:** (1) the all-declarations zig build's symbols are in the `spec_all` namespace, so a filter on `spec.` read 0 bytes; (2) rustc puts each function in its own `.text.*` section, so reading `.text` alone gave 0; sizes now sum every `.text*` section; (3) t27b test names with spaces (ed25519) were not parsed from `TIME` lines, so ed25519's t27b timing was re-run with a fixed parser (5 repetitions, same method, after the other timing passes); (4) max RSS read from the Python harness has an 11.5 MiB floor, so it was re-measured with a small helper. In each case the zero or the constant was noticed because it was implausible, then traced to the instrument.
- **Two statements in the brief did not hold at this commit:** t27b emits Mach-O only, not ELF; and "about 36% generated" holds for t27b's backend alone, 12% counting the front end it mounts.
- **One run of the corpus.** Coverage numbers come from one run per pipeline; 4 t27b files timed out at 60 s under qemu (2 time out in the reference too). The native CI run at the same commit gives the same t27b tally.


## How to reproduce

The harness is about 1,650 lines of lab-scratch Python, Zig and C and was not committed (#8236). These are the exact commands it ran, with `S` a spec path relative to the repository root and the working directory as noted. `QEMU` is `qemu-aarch64 -L /usr/aarch64-linux-gnu`.

Build, at the commit, with `CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER=aarch64-linux-gnu-gcc`:

```
cargo build --release -p t27c
cargo build --release -p t27b
cargo build --release -p t27b --target aarch64-unknown-linux-gnu
```

Axis A:

```
$QEMU t27b-aarch64 corpus specs --json out.json --runner "$QEMU" --timeout-ms 60000 --jobs 6 --reference t27c --reference-timeout-ms 300000
t27c gen S > spec.zig
zig test -target aarch64-linux -O {Debug|ReleaseFast} --test-runner runner.zig --test-no-exec -femit-bin=bin spec.zig
qemu-aarch64 bin          # lists "<i>\t<name>"; runner.zig is t27c test-report's RUNNER, verbatim
qemu-aarch64 bin <i>      # one test per process, exit 0 = pass, 120 s limit
t27c gen-c S > spec.c     # driver.c: declares every `void test_*(void)` gen-c emitted; no args lists them, <i> runs one
aarch64-linux-gnu-gcc -std=gnu11 -O{0|2} -static -w spec.c driver.c -o bin -lm
zig cc -target aarch64-linux-musl -std=gnu11 -O{0|2} -static -w spec.c driver.c -o bin -lm
t27c gen-rust S > spec.rs
rustc --edition 2021 --crate-type lib --target aarch64-unknown-linux-gnu -C opt-level=0 --emit=obj -A warnings -o spec.o spec.rs
```

Axis B (one process timed per sample; zig with a fresh `ZIG_LOCAL_CACHE_DIR` per sample and a warm `ZIG_GLOBAL_CACHE_DIR`):

```
t27b-x86_64 test S                     # exits 74 after code generation: "test-compile"
t27b-x86_64 build S -o t27b.o
$QEMU t27b-aarch64 test S --time --quiet   # phase times, for the calibration
aarch64-linux-gnu-gcc -std=gnu11 -O{0|2} -w -c spec.c -o x.o      # and the static exe line from axis A
zig cc -target aarch64-linux-musl -std=gnu11 -O{0|2} -w -c spec.c -o x.o
rustc ... -C opt-level={0|3} --emit=obj ...
zig test ... root.zig                  # batched: root.zig is `test { _ = @import("s00.zig"); ... }`
```

Axis C: the same binaries, built with a timing runner (zig) or the driver's `time` mode (C) that reads `CLOCK_MONOTONIC` around each test call and issues `getppid()` just inside those reads; t27b with `$QEMU t27b-aarch64 test S --time --quiet --overflow {trap|wrap}`. Instruction counts: the same commands under `qemu-aarch64 -plugin libicount.so`, where the plugin registers an inline add of each block's instruction count at block entry, a second counter for blocks whose address lies in a range passed to `mprotect` with `PROT_EXEC`, and a third that starts and stops at each `getppid` system call (number 173 on aarch64). Sizes: `aarch64-linux-gnu-nm -S --defined-only` (zig, symbols under the generated module's namespace, from a build of the spec with `test { @import("std").testing.refAllDecls(@This()); }` appended) and `aarch64-linux-gnu-size -A` (`.text*` sections of the objects).

Axis E: every command above, twice in one directory and once in another; `sha256sum` of every output.
