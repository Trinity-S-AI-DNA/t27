# NOW -- Trinity GitHub App: the golden criteria decided in t27, the workflow it installs, the app manifest (2026-10-11)

## specs/tools/t27o/golden.t27 + specs/tools/t27o/install.t27 (Refs #8997, epic #8998)

- The golden criteria have one home, in this project's own language: specs/tools/t27o/golden.t27 decides golden from recorded evidence (vectors agreed, translated tests passed, no duplicated t27 code per #8963, sealed, Sigstore attestation from the *producing* workflow run) and returns the first failing criterion as the report's refusal reason -- token-free, pinned by an invariant that the path spends 0 LLM tokens (the opt-in bee fallback #8969 is off it). The honesty clause is a line of the spec, not prose beside it: every report carries "golden means equivalent on the recorded vectors and translated tests, not a proof for all inputs", golden entries included, and the coverage badge floors (999 of 1000 reads 99; an impossible count refuses the badge rather than rounding up). Sealed: .trinity/seals/t27o_T27oGolden.json, 11/11 green, 0 vacuous (Railway lab).
- specs/tools/t27o/install.t27 (module T27oInstall) holds the workflow the app proposes on installation and the GitHub App manifest as string constants with semantic pins, a text_has helper and negative-control tests (sealed: .trinity/seals/t27o_T27oInstall.json, 11/11 green, 0 vacuous). The app copies WORKFLOW_YAML verbatim to .github/workflows/t27o.yml in the installed repository: dispatch with scan/golden/check modes plus golden on push, `contents: write` + `pull-requests: write` only, zero hand-written shell in the template (a negative-control test pins that; the shell that does exist lives in the commented fallback). It uses gHashTag/t27o-action@v1, the stable name the #8996 lane publishes; that lane has not landed, so a commented fallback that downloads the released signed binary and runs it directly rides along, and the PR says so.
- Why no .yml in this repository: hand-written .yml is denied by the owner language rule (specs/policy/own_language.t27), and the exception list (tools/policy/foreign-exceptions.txt) is owner-only and read from origin/master, so a branch cannot approve itself. The workflow template is the project speaking about itself, so its source is a .t27 spec; the .yml is materialized into the user repository at install time, and that repository is not bound by our rule. An in-repo .yml would need an owner exception entry or the owner-approved-foreign label -- neither faked here (the first commit attempt was rejected by the lefthook gate exactly as designed).
- The manifest (MANIFEST_YAML in the same spec) is machinery GitHub itself parses: installation, pull_request and workflow_run events, minimal permissions, public: false (own repos first, opt-in external after). The owner hosts the generated file at one URL for one-click registration (github.com/settings/apps/new?manifest=<raw URL>). It deliberately carries no webhook or redirect URL and no credentials -- NOT_IN_MANIFEST records why each belongs to the registered backend (t27-bees) or the owner; the exact owner steps (host manifest, register app, set APP_ID/PRIVATE_KEY secrets, choose repos, add the webhook) are a checklist on issue #8997.
- Server-side webhook behaviour is out of this PR by scope: not buildable before the app is registered. specs/tools/mcp/trinity.t27 gains one pointer comment disambiguating the Trinity GitHub App from the trinity MCP server card it sits in.
