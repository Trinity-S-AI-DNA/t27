## Goal

`specs/tri/shootout/codegen_audit.t27` and `specs/tri/shootout/acceptance_matrix.t27` each
discard 4 tokens at parse, so the corpus ratchet fails both under `parse-no-discard`. Both
discard the same line, and `t27c parse-complete --specs-dir specs/tri/shootout --show <spec>`
(W634) names it rather than inferring it:

```
24| use tri::shootout::bench::MEASURED_T27B_BASELINE;
    dropped: : : MEASURED_T27B_BASELINE ;
```

The cause is #11101 with `bench` in place of `test`: `"bench" => TokenKind::KwBench`
(`bootstrap/src/compiler.rs:453`) against a `use` path loop that accepts only
`TokenKind::Ident`, so the path truncates to `tri::shootout::`, the stray `bench` opens a
bench block at module level, and the clause machinery discards the remaining four tokens.
`specs/t27os/glass_window.t27` carries about 20 `use t27os::bench::X;` lines and is among the
48 discarding specs, so this is a corpus-wide limitation rather than a quirk of these files.

Two facts make the spec side an issue of its own.

**No spelling reaches a module at a keyword path.** All branches of the `use` parser were read:
the `::` loop and the dotted branch (#5978) both require `Ident` after the separator; the
braced list (W630) requires `full_path.ends_with("::")` and `Ident` inside the braces; the
alias form `using x: @import("...")` parses cleanly but `use_resolve::use_path_expr` reads
only lines beginning `use `, so it splices nothing. `use_target` drops a single trailing
segment, so the only two spellings that name `specs/tri/shootout/bench.t27` are
`tri::shootout::bench` and `tri::shootout::bench::Item`, and both carry the keyword.

**The import is live, not dead.** `cli/t27b/src/front.rs` resolves `use` by splicing the
imported declarations into the raw text before parsing, and `cli/t27b/src/lower.rs:755`
ignores `UseDecl` when lowering, so the four-segment path resolves correctly while the parse
stays dirty. The value is consumed at `codegen_audit.t27:352`, `:492`, `:493` and
`acceptance_matrix.t27:732`, and `t27c check` prints `Typecheck OK (0 errors, 0 warnings)` for
the spec exactly as it stands -- so a clean typecheck is not evidence that the line can go,
and deleting it would break those asserts.

The ledger workaround that #11101's FR-003 names is not available: `suite_expectations.json`
holds 75 entries against `max_entries: 75`, W699 requires a volume number on a discard-phase
row, and rows are the steward's.

What remains is the remedy #10233 took and recorded as its FR-001 -- "The spec MUST NOT import
through a path segment that is a keyword" -- applied to the provider side. A measured value
that nothing can import does not belong at a keyword path.
