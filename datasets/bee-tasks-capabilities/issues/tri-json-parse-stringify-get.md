# Write the RFC 8259 parser, serializer and object lookup in specs/tri/encoding/json.t27

`.t27` is the hand-authored source language of this project. `t27c` compiles it out — `t27c gen` emits Zig, `t27c gen-verilog` emits Verilog. You are writing **source**, not compiler output. Everything below is to be written in `.t27` inside `specs/tri/encoding/json.t27`. Do not hand-edit anything under `gen/`; it is regenerated and carries `// DO NOT EDIT — generated by t27c`.

A real imperative body survives codegen intact — this is not a language limitation you have to work around. Measured on a scratch copy of this very file (a linear-scan `get` written in `.t27`, then `t27c gen`):

```
fn get(obj: JsonObject, key: []const u8) ?JsonValue {
    var i: usize = 0;
    var found: ?JsonValue = null;
    while (i < obj.entries.len) {
        if (std.mem.eql(u8, obj.entries[i].key, key)) {
            found = obj.entries[i].value;
        }
        i = i + 1;
    }
    return found;
}
```

## Context: what this module is for

`specs/tri/encoding/json.t27` is 66 lines, module `TriJson`, one of eight encoders in `specs/tri/encoding/` (`bson`, `csv`, `html`, `json`, `markup`, `mime`, `msgpack`, `xml`). Its own header states the contract it is held to:

```
// RFC 8259 compliant | φ² + 1/φ² = 3 | TRINITY

module TriJson;
    use base::types;
    use math::constants;
```

The whole type section, verbatim, lines 13-27 — this is the contract the three functions operate on:

```
    pub const JsonValue = struct {
        type : JsonType,
        data : *JsonValueData,
    };

    pub const JsonType = struct {
        enum : [Null, Bool, Number, String, Array, Object],
    };

    pub const JsonArray = struct {
        items : []JsonValue,
    };

    pub const JsonObject = struct {
    };
```

Two of those declarations are holes, and they are the reason nothing in this module compiles today.

**`JsonValueData` is referenced and declared nowhere.** `JsonValue.data` is a `*JsonValueData`, and that name occurs exactly once in the entire spec tree — at its own use site:

```
$ grep -rn 'JsonValueData' specs/
specs/tri/encoding/json.t27:15:        data : *JsonValueData,
```

**`JsonObject` has no fields at all**, so it is a zero-sized type: an object cannot carry a single member, and `get(obj, key)` has nothing to look in. The corpus already knows this failure shape — `specs/tri/encoding/csv.t27` carries a test named `a_row_can_hold_at_least_one_cell` with the comment "FAILING ON PURPOSE. CsvRow is declared with no fields at all, so it is a zero-sized type". `JsonObject` is the same defect, undocumented.

The sibling that already solved the tag-plus-payload problem is `specs/tri/encoding/msgpack.t27`, which declares one tag field and one payload field per kind on a single struct:

```
    pub const MsgPackValue = struct {
        type : MsgPackType,
        int_value : i64,
        uint_value : u64,
        float_value : f64,
        str_value : []const u8,
        bin_value : []const u8,
        array_value : []MsgPackValue,
        map_value : std.StringHashMap(MsgPackValue),
    };
```

`JsonValue` has already chosen a different split — the tag on `JsonValue.type`, the payload behind a pointer in `JsonValue.data`. That split is the module's decision and stands; what is missing is the `JsonValueData` struct it points at.

## What to write

### 1. Close the two type holes

Declare `JsonValueData` as the payload `JsonValue.data` points at, with one field per non-trivial kind — `Null` carries nothing, so it gets no field. Declare a member type and give `JsonObject` a slice of it, mirroring `JsonArray`'s own `items : []JsonValue` shape, so that `get` is a linear scan over a slice. Required shape:

```
    pub const JsonMember = struct {
        key : []const u8,
        value : JsonValue,
    };

    pub const JsonObject = struct {
        entries : []JsonMember,
    };

    pub const JsonValueData = struct {
        bool_value : bool,
        number_value : f64,
        string_value : []const u8,
        array_value : JsonArray,
        object_value : JsonObject,
    };
```

Do not change `JsonValue`, `JsonType` or `JsonArray`. The tag lives on `JsonValue.type`; `JsonValueData` carries no tag of its own.

### 2. `fn parse` — signature verbatim, do not change it

```
    // parse(text: []const u8, allocator: std.mem.Allocator) → !JsonValue
    fn parse(text: []const u8, allocator: std.mem.Allocator) -> !JsonValue {
```

A recursive-descent parser over `text`, allocating every `JsonValueData`, every `JsonArray.items` and every `JsonObject.entries` out of `allocator`. **The required subset is exactly RFC 8259 and nothing more** — "implement JSON" is not a contract, so this is the contract:

- **Values.** All six of `JsonType`: `null`, `true`/`false`, number, string, array, object. The top-level value may be any of the six (RFC 8259 §2), not only an array or object.
- **Whitespace.** Exactly the four bytes of §2 between tokens: space `0x20`, tab `0x09`, LF `0x0A`, CR `0x0D`. No others, and comments are not whitespace — `//` and `/* */` are an error.
- **Numbers** (§6). `-`? int `.`frac? (`e`|`E`)(`+`|`-`)?digits? , decoded into the `f64` field `number_value`. Reject a leading `+`, a leading zero on a multi-digit integer (`01`), a bare `.5`, a trailing `.` (`1.`), hex, and the literals `NaN`, `Infinity`, `-Infinity`. There is no integer/float distinction in `JsonType` — every number is an `f64`.
- **Strings** (§7). The eight two-character escapes `\" \\ \/ \b \f \n \r \t`, plus `\uXXXX` with exactly four hex digits. A high surrogate `\uD800`-`\uDBFF` **must** be followed by a low surrogate `\uDC00`-`\uDFFF` and the pair decoded to one code point, UTF-8 encoded into `string_value`; a lone surrogate on either side is an error. Any unescaped byte in `0x00`-`0x1F` inside a string is an error. Any other `\x` escape is an error.
- **Structure.** Reject a trailing comma in an array or object, a missing `:` between key and value, a non-string object key, and any non-whitespace byte after the top-level value.
- **Duplicate keys.** Last one wins. Keep every member in `entries` in source order; `get` resolves the tie.
- **Depth.** Declare `pub const MAX_DEPTH : u32 = 128;` and return an error when nesting would exceed it, rather than recursing until the stack dies. Input nested 32 levels deep must parse successfully.
- Errors are returned through the declared `!` error union. Do not `@panic` on malformed input — malformed input is the normal case for a parser.

The file's own body comment today reads `// TODO: Implement from .tri spec`; replace it with the implementation.

### 3. `fn stringify` — signature verbatim, do not change it

```
    // stringify(value: JsonValue, allocator: std.mem.Allocator) → ![]u8
    fn stringify(value: JsonValue, allocator: std.mem.Allocator) -> ![]u8 {
```

The inverse of `parse`, allocating its result out of `allocator`. Required:

- Compact output: no spaces, no newlines, no indentation. `{"a":1,"b":[true,null]}`.
- Escape on output exactly what §7 requires and nothing else: `"` `\` and the C0 controls `0x00`-`0x1F` (using `\b \f \n \r \t` where they exist, `\u00XX` otherwise). Do **not** escape `/`, and do not emit `\uXXXX` for characters above `0x1F` — pass valid UTF-8 through byte for byte.
- Numbers must be formatted so that feeding the output back to `parse` yields the same `f64`.
- `parse(stringify(v)) ` must be structurally equal to `v` for every value `parse` can produce. Object members are emitted in `entries` order.

### 4. `fn get` — signature verbatim, do not change it

```
    // get(obj: JsonObject, key: []const u8) → ?JsonValue
    fn get(obj: JsonObject, key: []const u8) -> ?JsonValue {
```

Byte-exact lookup of `key` in `obj.entries`, returning `null` when absent. No allocator, no error union — it cannot fail. Consistent with parse's duplicate-key rule: when `entries` holds the same key twice, return the **last** one. A linear scan is correct and expected; `entries` is a slice, not a hash map.

### 5. Replace the three stub tests

Delete `parse_basic_case`, `stringify_basic_case` and `get_basic_case` — they pass one argument to two-parameter functions and codegen discards them anyway. Write at least six real tests. `specs/tri/net/http.t27` is the working model in this directory family: it is the one spec among the capability files whose `t27c test-report` reports `tests 5 / pass 5 / FAIL 0`.

Three traps in the `.t27` test DSL, each measured on a scratch copy of this file rather than assumed:

- `then @FieldType(JsonObject, "entries") == []JsonMember` **does not compile**. A slice-of-struct type on the right of `==` lowers to something Zig rejects with `error: incompatible types: 'type' and '@TypeOf(.{})'`. `specs/tri/encoding/csv.t27` is BLOCKED today for exactly this reason. Write `then @typeInfo(@FieldType(JsonObject, "entries")).pointer.child == JsonMember` instead — verified to compile and pass.
- A list literal `[a, b]` in a `given` lowers to an anonymous tuple `.{a, b}`, not to an array, so it cannot be assigned to a `[]JsonMember` field.
- A module-level `const NAME : []JsonValue = &[_]JsonValue{};` is silently dropped by codegen — the name then does not exist in the emitted Zig, while `t27c parse` still reports `0 0 0`.

## How to check

The empty-body count is the primary gate, and it must be measured by **brace matching, not by a marker string**. `grep -c 'TODO: Implement'` is not a valid check here: four of the six capability specs in this batch write `// Implementation: ...` instead, and a marker grep reads an entirely unwritten file as finished. Run exactly this, from `/Users/playom/t27`:

```
python3 - <<'EOF'
import re
t=open("specs/tri/encoding/json.t27",encoding="utf-8").read()
n=0
for m in re.finditer(r'(?m)^\s*(?:pub\s+)?fn\s+(\w+)\s*\(', t):
    i=t.find('{', m.end()); semi=t.find(';', m.end())
    if i<0 or (semi!=-1 and semi<i): continue
    depth=0; j=i
    while j<len(t):
        if t[j]=='{': depth+=1
        elif t[j]=='}':
            depth-=1
            if depth==0: break
        j+=1
    b=re.sub(r'/\*.*?\*/','',t[i+1:j],flags=re.S); b=re.sub(r'(?m)//.*$','',b)
    if not b.strip(): n+=1
print("empty bodies:", n)
EOF
```

It prints `empty bodies: 3` today.

Never pipe `t27c parse` through `tail -3`. On a dirty file a `recovery-at:` line is printed between `recovery-events:` and `declarations-swallowed:`, and further `discarded:` diagnostics follow the metrics, so `tail -3` hides the number that matters. Use the `grep -E` form quoted in the criteria.

`t27c typecheck --json` returns `{"ok":true,"errors":0}` on plain English prose. It proves nothing and is not a criterion.
